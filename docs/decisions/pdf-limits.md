# PDF decisions: resource limits, page boxes and attachments

Decisions of the PDF extractor (`src/opendockit/extractors/pdf.py` and the `_pdf_*.py` modules beside it) about resource limits (time budget, decompression, font ranges, overdrawn copies, text-box grouping, rendering, pdfminer logging), page boxes and attachments. Split off from [pdf.md](pdf.md)
because of its size limit; the rules are the same: do not revert the decisions in this table. To change one, change the pinning test first and write the reason in the same row.

## PDF resource limits

| Decision | Why | Pinned by |
| --- | --- | --- |
| Pages beyond the PDF time budget (default 60 seconds) go to pdfium | A 102-page PDF of vector shapes went from 184 seconds → 62 seconds, with the text preserved | `test_pdf.py::test_time_budget_reads_remaining_pages_with_pdfium` |
| If the number of line pieces obtained by joining a page's text chunks (pdfium `count_rects`) (`_text_line_pieces`: joined when they overlap vertically by half or more and the horizontal gap is at most the height) exceeds 2,000, that page is read without text-box grouping (`boxes_flow`) and a warning is issued. The limit value is the owner's decision. The ruled-grid judgment (`_is_ruled_grid`) uses the raw chunk count | Grouping grows quadratically, so a page of 4,700 scattered characters took 54 seconds and 3.2GB. The maximum over 993 pages of public PDFs is 1,900. Chrome places Hangul separately per character, so chunks are 71% of the character count (LibreOffice 13%), and an ordinary two-column paper page (about 2,900 characters, 2,136 chunks → 103 line pieces) hit the limit and the column order was mixed (round 34). The cost of grouping depends on the number of text boxes, and there are no more text boxes than line pieces. Scattered characters stay separate and are still caught (2,500 → 2,431) | `test_pdf.py::test_page_of_thousands_of_scattered_text_pieces_is_read_without_box_grouping`, `test_pdf_resource_limits.py::TestGlyphByGlyphText` |
| The per-page running check of the character limit (`_countable_chars`) does not count dots, middle dots and ellipses (`_LEADER_DOTS`) | The leaders of a table of contents shrink to a single ellipsis only after the whole page text has been gathered (`_shortened_leaders`), and some become leaders only after pieces are joined, so the share to be shortened cannot be known per piece. Counting them rejected a table-of-contents document whose result is 2,741 characters as exceeding a limit of 8,223 characters (round 36) — the running check must never be larger than the character count of a full conversion (the `exceeded` row in [core.md](core.md)) | `test_pdf_toc_and_checkboxes.py::TestDotLeaderPageNumbers::test_long_dot_leaders_do_not_count_against_the_limit_before_they_are_shortened` |
| The per-page running check of the character limit (`_countable_chars`) counts text read sideways (`page.sideways`) and form values (`page.form_values`) as well as lines and tables, with the same `(cid:n)` and leader-dot exclusions | Both are always written at the end of the page, yet were left out, so a document whose text is all rotated by 90 degrees (200 pages under a 5,000-character limit) was analysed page after page until the 60-second time budget stopped it | `test_audit_pdf_text.py::TestLimitCountsSidewaysTextAndFormValues` |
| The running check does not count edge lines that may be erased as repeated lines (the edge area and the two top and bottom rows), but does count a line that would fall short of the repetition criteria (half of all pages, 2/3 of the odd or even pages, at least 3 pages) even if it appeared on every remaining page to the end (the `limit` page) (`_EdgeTally`, counted on the text with digits masked and spaces removed). If the setting is not to erase repeated lines, everything is counted. Known accepted gap: for a little over the first half of the pages, edge lines are still not counted | In a slide-type document with one or two lines per page every line is an edge line and was counted as 0 characters, so 75 pages of lecture slides (5,493 characters) were analysed to the end even at 10% of the limit, and a 1,500-page document took 7–11 seconds (round 48). The repetition key (`_row_key`) masks only some digits, so lines with the same key also have this same text, and nothing is overcounted (the `exceeded` invariant). The slack up to the criteria shrinks more slowly than the number of remaining pages, so checking it only against the last page is correct wherever the conversion stops | `test_pdf_round48.py::TestEdgeLinesThatCannotRepeatCount` |
| PDF rendering bitmaps are at most `_MAX_RENDER_PIXELS`; on a page that exceeds it only the picture area is rendered | An 8000pt page took 9.4GB | `test_image.py::TestResourceBounds::test_pdf_figure_on_a_huge_page_renders_only_its_own_area` and 1 more |
| A page with more than 50,000 PDF drawing objects (`_MAX_PAGE_OBJECTS`, including those inside forms) gets pdfium plain extraction without pdfminer + a warning | A single page of 240,000 Form XObjects took 65 seconds and 4.6GB (it has only 280 text pieces, so it passed the existing check). The maximum over the 993-page sample is 12,500 | `test_pdf.py::test_page_with_huge_number_of_drawing_objects_is_read_with_pdfium` |
| The decompression limit (`max_uncompressed_bytes`, the same value as for ZIP·HWP and the same `DocumentTooLargeError` saying the document becomes too large when decompressed) is applied to all PDF streams (`_InflateBudget`). The whole document is rejected (not just the page skipped — the limit is a document total). It is charged in two places: every stream decode of pdfminer (`PDFStream.decode` replaced with `_decode_within_budget` — including object and cross-reference streams; a `ContextVar` only during conversion), and the content streams and resources of a page before pdfium opens it (`_charge_page`). The size is measured by inflating 1MB at a time (`_inflated_size`). Picture XObject and attachment streams are not measured. Exceptions wrapped by pdfplumber are also checked before falling back to pdfium plain extraction (`_check_budget`). Known limitation: documents pdfminer cannot open at all and that are read with pdfium only, and the LZW·RunLength stages, are not measured | The content stream of a 760KB PDF (800MB when inflated) was inflated whole in the pdfium survey and again in pdfminer, using 2.49GB and 3.5 seconds → rejected at 90MB and 0.5 seconds. pdfium inflates first during the page survey, so blocking only pdfminer is useless. Object streams are inflated when pdfminer looks up an object, and treating that failure as 'structure analysis failed' makes pdfium inflate them again. Pictures: large scanned documents would hit the limit, and they are not inflated for reading text (rendering is covered by `_MAX_RENDER_PIXELS`) | `test_pdf_resource_limits.py::TestDecompressedStreamBudget` |
| A page with more than 1,000 text chunks (`_GRID_MIN_TEXT_PIECES`) and at least half as many lines and shapes (pdfium paths) (`_is_ruled_grid`) is also read without text-box grouping. No warning is issued. Known accepted gap: text outside the table on such a page is in top-to-bottom order | A page of a ruled table with 1,210 cells was below the 2,000 threshold and spent 3.6 seconds per page on grouping, so a 30-page document went over the time budget from page 18 and became plain extraction without tables → 30 pages in 16 seconds, tables on every page. Cell text moves into the table, so there is no order for grouping to decide | `test_pdf_resource_limits.py::TestLargeRuledGrid` |
| The `/W`·`/W2` ranges of CID fonts and the bfrange·cidrange of mapping tables (ToUnicode and Encoding CMaps) are expanded only up to 130,000 entries per font (`_FONT_RANGE_ENTRIES`) and 2.1 million entries per document (`_DOCUMENT_FONT_RANGE_ENTRIES`); a range beyond that has its end cut off with a warning (that the range is abnormally large). pdfminer functions are not copied: the array is shortened before it is passed to `pdffont.get_widths`·`get_widths2`, and the accumulated ranges are shortened at `endbfrange`·`endcidrange` in `CMapParser.do_keyword` (only during conversion) | pdfminer expanded the ranges `/W [40000 400000000 500]`·`<00000000> <05F5E100>` of a 3KB PDF into a dictionary entry by entry and used tens of GB (outside the decompression limit). By the specification a mapping-table range stays within the last byte (256 entries), so ordinary documents never reach it. With only a per-font cap, thousands of small font dictionaries do the same thing | `test_pdf_resource_limits.py::TestFontRangeBounds` |
| Copies of the same character drawn at the same place (character, font, size, position to 0.1pt; a NaN value is keyed as None) more than 3 times (`_MAX_OVERPRINTS`) are discarded as soon as the layout object is created (wrapping pdfplumber `render_char`, only during conversion). Fake bold (two or three times) is still handled by copy removal. Known limitation: copies drawn slightly shifted each time are not reduced | A 106KB page that repeated its content stream thousands of times grew with the square of the number of copies in pdfminer line grouping and piece merging (`_merged_overlapping_pieces`, `get_text` per pair), taking 110 seconds and 2.2GB (repeating the `/Contents` array exceeded 3GB) → 0.2 seconds and 90MB. NaN is unequal even to itself, so 20,000 copies at a NaN position (a text matrix overflowing to infinity, 860 bytes) were never capped and took 39 seconds | `test_pdf_resource_limits.py::TestOverprintedText`, `test_audit_pdf_text.py::TestCharactersAtNonFinitePositions` |
| During conversion the `pdfminer` logger is raised to ERROR and restored when the last conversion ends (concurrent conversions are counted, `_quiet_pdfminer`). Known accepted gap: during conversion, pdfminer warnings from elsewhere are not visible either | 'Could not get FontBBox' for every font missing its font descriptor flooded the server's stderr. The result is the same, and anything worth reporting is the job of the warning list | `test_pdf_resource_limits.py::TestPdfminerLogNoise` |
| Before pdfium or pdfminer opens a page, the number of objects it will draw is estimated (`_drawn_objects`: text, shape, shading and inline-image operators of the content streams + for each form `Do`, the number of times drawn × (1 + the count inside the form); each form is counted once, a form that comes back to itself counts as 1, and a chain deeper than 32 levels (`_FORM_NESTING_MAX`) is over the limit). Pages without forms are counted too — a content stream shared by several pages is counted once per document (`_InflateBudget.painted`). A page over 500,000 (`_MAX_DRAWN_OBJECTS`) is opened by nobody and becomes an empty page + a warning (that it was not read because it has too many drawing elements or its forms (Form XObject) are nested too deeply). The page survey (`_survey_page`) also counts inside forms down to 32 levels (pypdfium2 default 15 levels). Known limitation: drawing repeated through patterns or Type3 fonts is not counted. Known accepted gap: on a page with more than 500,000 drawing operations (very dense drawings or maps) the text is not read either | A 7-level chain in which each form draws the next form 10 times (3.4KB, 2.1 million objects) used 5.9GB just by pdfium opening the page (round 35). A 253KB file repeating `0 0 1 1 re f` 10 million times without forms took 3.6GB and 19 seconds, 143 seconds when 40 pages share one stream; a 6.8KB file multiplying below level 15 took 3.3GB and 21 seconds without a warning, and a 10KB file multiplying below level 32 took over 12 minutes (round 37). A stream is measured only once per document (`walked`), so the decompression limit cannot block it, and `_MAX_PAGE_OBJECTS` is counted after pdfium has opened the page. pdfium needs about 2.8KB per form object and about 0.4KB per rectangle, so 500,000 means 1.4GB·0.2GB — the page of 240,000 Form XObjects gets plain extraction as before | `test_pdf_resource_limits.py::TestRepeatedFormXObjects`, `TestManyPaintOperators`, `TestDeepFormsAreSurveyedToTheBottom` |
| Joining horizontal rules of a table open on the left and right (`_joined_rules`) keeps the ended lines per (height, end x) in order of end x and looks only at the first line in the joinable end-x range (for the same end x, the line placed first). Known accepted gap: when several lines are joinable, the line with the smallest end x is joined, unlike before (the line placed first) — this happens only with lines overlapping at the same place | The list of ended lines was scanned from the start for every line, so a 2KB PDF filling a 1pt rectangle 45,000 times at the same place took 457 seconds (none of the overlapping lines was joined, so the list grew without end, round 37) | `test_pdf_resource_limits.py::TestStackedRules` |
| `_read_page` picks the characters of layout lines at the same place (x0·x1·top·bottom) only once (`in_place`), and a following line with the same place and text as a line that kept its text as is despite having copies beside it is discarded without scanning the copies (`overprinted`). That line has the same copies too and `_text_without_artifacts` always discards it, so the output is the same. The character spacing estimate (`_letter_spacings`) looks at the same group of characters only once (an equal gap is kept only once, so the result is the same) | A 3.2KB PDF overdrawing the same text 16,000 times at the same place through a form scanned all characters and copies at that height for every line and took 52 seconds (lines × copies, round 37). No output difference on the PDF corpus of past reviews | `test_pdf_resource_limits.py::TestOverprintedCopiesOfOneLine` |
| Every Flate stage of a stream is charged (`_charge`); a stage followed by another Flate stage is measured, then decoded by pdfminer's decoder to feed the next measurement. Known limitation: LZW and RunLength stages are still not measured | `/Filter [/FlateDecode /FlateDecode]` passed the limit on its first stage; a 1.1 KB PDF inflated to 200 MB under a 10 MB limit | `test_audit_pdf_head.py::TestStreamCompressedTwice` |
| Charged streams are keyed by (object number, generation), by `id` only when there is no number | The second pdfplumber document for dense pages builds new stream objects, so a page inflating to 6.4 MB was charged twice and rejected at 10 MB | `test_audit_pdf_head.py::TestStreamReadThroughTheUngroupedDocument` |
| A page pdfium cannot open on the normal path is an empty page or keeps the pdfminer result, with the existing time-budget or structure-failure warning. Known accepted gap: a document pdfium cannot open at all still fails | `/Count 1` over two `/Kids` made the whole document 'corrupted' although page 1 was readable | `test_audit_pdf_head.py::TestPageOnlyPdfminerFinds` |
| `_merged_overlapping_pieces` compares only pieces overlapping in x and within 2 / `_PIECE_HEIGHT_RATIO` heights; the y0 scan is kept for non-finite boxes. Known accepted gap: `_chars_at_line_level` and the per-line x filter in `_read_page` are still quadratic for one long row | One row of 6,000 two-letter pieces (8.5 KB) took 28 s inside one page | `test_audit_pdf_head.py::TestManyPiecesOnOneBaseline` |
| `_mark_checkboxes` finds touching rectangles through a 64 pt grid of top-left corners. Check marks are looked up by the 64 pt grid cell of their centre (`_MarkIndex`), curve boxes are grouped through a grid of their first shape's corner (`_CornerGrid`, first group in creation order as before), the 'another box on this row' test is a binary search over group tops (`_GroupRows`), and circle bullets find their line by a binary search over line tops (`_LinesSpanning`); all give exactly what the full scans gave. Known accepted gap: rectangles over 64 pt, and the chars / lines scans per box, are still linear per box | 10,000 separate 8 pt squares took 17 s; 5,000 small circles (166 KB) took 35 s in curve grouping and the tick and row scans | `test_audit_pdf_head.py::TestManySquaresOnOnePage`, `test_audit_pdf_text.py::TestManyCurveBoxes` |
| `_content_objects` looks at only the first `limit + 1` XObject calls, and one annotation that cannot be read drops only its own form value | `findall` on a 65 MB stream of 5M distinct names held 500 MB; one bad `/Rect` dropped every form value of the page | `test_audit_pdf_head.py::TestManyDistinctXObjectNames`, `TestOneUnreadableAnnotation` |
| A sideways cell takes its characters from lists sorted once by vertical and by horizontal middle, filtering the shorter of the cell's two ranges, in page order | Scanning the page per cell took 23 s on a 10 KB table of 100×20 sideways cells; a vertical-only bisect made one-row tables slower | `test_audit_pdf_mid.py::TestSidewaysCells` |
| Per-page lists for tables (vertical rules by x, characters by middle, sideways characters) are built once per page, tied to `page.objects`, and dropped by `_real_tables` | 800 small tables spent 9 s re-listing the page per table; pdfplumber keeps Page objects after `close()`, so lists left on them would hold every page's characters and serve stale ones on a re-read | `test_audit_pdf_mid.py::TestManyTablesOnOnePage` |
| Abutting pictures are found among boxes with a side near the opposite side, enclosing pieces among those starting where an encloser must start, the union area by a sweep; non-finite coordinates take the old all-pairs path | 3,000 vertical strips sharing a top took 10 s in a 12 KB file; the pairs and sums must stay exactly the same | `test_audit_pdf_mid.py::TestPictureDrawnAsManyStrips` |
| A fill rectangle takes its characters from its line or from between its edges, whichever are fewer, and growing a shaded table measures each fragment once. Known accepted gap: `_open_sided_tables` crops the page once per region (400 open-sided tables of distinct widths: 5 s) | 4,000 rectangles on one line of 4,000 characters took 8 s (15 KB); a striped table of 2,000 rows took 7 s | `test_audit_pdf_mid.py::TestManyFilledRectanglesOnOneLine`, `TestLongStripedTable` |
| While wrapped lines are added to a borderless table row, its bottom is carried along and the cell columns come from `_cell_columns`, which gives exactly the `_column_of` result; `_label_value_run` carries the wrapped-value flag. Known accepted gap: both stay quadratic | 600 one-word lines under one row (3.8 KB) took 8–10 s; 1,500 pairs with long labels took 12 s | `test_audit_pdf_tail.py::TestManyWrappedLinesUnderOneRow`, `TestManyPairsWithLongLabels` |
| `_LEADER_END` and `_LEADER_TAIL` start a dot run only at its first dot, and `_PAGE_NUMBER` has no two neighbouring optional white-space runs; same verdicts | 20,000 dots followed by a word (1.4 KB) took 12–18 s (quadratic backtracking); the page-number pattern was cubic on a digit followed by white space | `test_audit_pdf_tail.py::TestLongDotRunInsideALine`, `TestPageNumberShape` |
| The label of a FreeText annotation is found through an index of the page's lines by top edge (`_LinesBeside`, exactly the line a full scan picks), and a page looks at no more than `_LABEL_SEARCH_WORK` (2,000,000) candidate lines in all; after that the remaining annotations get no label (their values still come out). Known accepted gap: on such a page the later values lose their 'label: ' | Every annotation scanned every line: a 38 KB PDF with 200,000 FreeText annotations (an object stream) over 1,800 lines took 52 s inside one page, where the time budget never looks. Boxes as tall as the page make every line a candidate, so the index alone does not bound it | `test_audit_pdf_text.py::TestManyFreeTextAnnotations` |
| Splitting a line at its gaps (`_gap_parts`) looks up the line's space characters by binary search on their x0 (`_SpaceStarts`, same spaces in the same order as a scan) | One 659-byte line of 16,000 letter-spaced words took 36 s (every gap and every piece scanned every space) | `test_audit_pdf_text.py::TestLongLetterSpacedLine` |
| The faint-watermark test (`_faint_watermark`) looks for overlapping characters through rows of cells, one level per size (`_CharGrid`: cells of 64 pt × 8^k, the first level at least a character's larger side; each row sorted by left edge and searched by binary search, candidates given lazily so the first overlap ends the search; every finite character is indexed whatever its magnitude, boxes are taken with their corners in order, characters with a NaN coordinate are left out — they fail every comparison of the overlap test — and only characters with an infinite coordinate are always looked at), with the same overlap test | The groups are keyed by exact colour, so a 41 KB page of 5,000 faint characters in slightly different greys scanned every character per character and took 13 s. A single 64 pt grid kept every character larger than a cell aside — exactly the size of a watermark — so 6,000 faint 70 pt characters still took 2.2 s (18,000: 22 s) and an 85 KB page of 12,000 spent 12.5 s here. Characters beyond 1e9 pt were kept aside too, and they do reach this test (it runs before the out-of-view filter): 12,000 distinct ones far off the page took 7.2 s | `test_audit_pdf_text.py::TestManyFaintCharacters` |
| A layout line whose box reaches pdfminer's 'infinite' value (2**31 − 1) is not read, and line pieces with coordinates that are not finite numbers are not joined (`_piece_joints`) | A text matrix overflowing to infinity puts characters at NaN positions. Rounding such a piece's position raised ValueError and the whole document was reported corrupted; with that fixed, the characters (already dropped as outside the view) still came out as body lines through their layout line. No page reaches that far (14,400 pt × UserUnit 75,000) | `test_audit_pdf_text.py::TestCharactersAtNonFinitePositions` |
| Re-reading the pages that could not determine the width of separately placed text (`placement_pending`) stops once the time budget is spent; such a page keeps its first reading. Known accepted gap: its words placed without spaces stay joined | Re-reading ignored the budget, so after the budget had sent the remaining pages to plain extraction every pending page was still analysed a second time | `test_audit_pdf_text.py::TestPendingPagesAfterTheTimeBudget` |

## PDF page boxes and attachments

| Decision | Why | Pinned by |
| --- | --- | --- |
| The MediaBox·CropBox of a pdfminer page are corrected to the order (lower left, upper right) before layout analysis (`_normalize_page_boxes`). A box that is not four numbers is not touched | By the specification a box may be written with any two corners (`[0 842 595 0]`). pdfplumber corrects the page size, but pdfminer shifts characters using the y of the first corner as the origin, so all characters ended up outside the visible area and were erased (the 'no text was extracted' warning) | `test_pdf_page_boxes.py::TestReversedPageBoxes` |
| Attachments (the catalog's `/Names /EmbeddedFiles` name tree — up to 10,000 `/Kids` nodes — and FileAttachment annotations of the pages read) are not read; a warning says that the N PDF attachment(s) (names, …) were not read and should be converted separately (same form as the mail attachment warning; the name is `/UF` → `/F` → name-tree key, equal names are merged, and beyond 10 it says 'and N more'). Deliberate exception to the AGENTS.md rule that warnings never include document content: the attachment names are the only way to tell the user which files to convert separately | Attachments dropped out without a warning. Attachments come in all kinds of formats and are converted when uploaded separately | `test_pdf_attachments.py::TestEmbeddedFiles` |
| Measuring the inflated size (`_inflated_size`) stops at the zlib end (`eof`) | For a content stream over 1MB whose `/Length` also counted the trailing newline, the bytes after the end stayed in `unconsumed_tail` and the conversion never finished (100% CPU, not even heeding the time budget, round 38). pdfium and pdfminer read it normally | `test_pdf_resource_limits.py::TestStreamWithBytesAfterTheZlibEnd` |
| The fallback path for documents pdfminer could not open (`_read_with_pdfium`) also reports the character count per page and stops when the limit is exceeded. The time budget is not checked (the point of the budget is to switch to plain extraction when it is exceeded, and this is plain extraction from the start). Known accepted gap: this path cannot apply the decompression limit or the drawing-object estimate before opening a page (pdfminer cannot parse the pages) | A 200-page document with 300,000 characters per page read 101 pages for over 122 seconds on a 10-second budget (round 38) | `test_pdf.py::TestPdfiumFallback::test_document_pdfminer_cannot_open_stops_reading_pages_once_the_character_limit_is_exceeded` |
| Plain extraction (`_simple_page`) looks for the presence of pictures only on pages without text. The drawing-object estimate counts the number inside a form once per document (`_InflateBudget.forms`; a form that draws no other XObject is the same one regardless of resources) | The presence of pictures is used only for the scan judgment, yet all objects of the page were scanned in Python, and the estimate recounted a shared form on every page. A 110KB file in which 300 pages draw a form of 400,000 operations took about 1 second per page even after the budget was exceeded (225 seconds, round 38). What remains is the time pdfium takes to open a page (about 0.35 seconds per page) | `test_pdf_resource_limits.py::TestSimpleReadingOfPagesWithText`, `TestFormSharedByPages` |
| Picking the characters of a band when widening shaded tables (`_band_chars`) slices only the band height out of the characters sorted once per page by top edge (`_chars_by_top`, one of the per-page lists for tables, dropped by `_real_tables` — kept on the page object by itself it held every page's characters and gave a page read again its old characters, `test_pdf_shaded_tables.py::TestCharactersByTop`) | All characters of the page were scanned for every band, so a large page with many filled bands and tables (1500pt square, 50,000 characters, 196 tables) took 48 seconds, and the 3000pt version over 8 minutes (inside a page, so the time budget does not apply either, round 41). Now 2.3 seconds and 12.5 seconds | `test_pdf_shaded_tables.py::test_many_bands_on_a_page_with_many_letters_take_linear_time` |
| 'Is this character inside a cell' in page reading (`_read_page`, `_closed_at_the_bottom`) is answered with an index that divides cell boxes into 16pt-high bands (`_BoxIndex`). Marking filled cells (`_mark_filled_cells`) picks, per row, only the fill rectangles reaching that row's height by sweeping from top to bottom (`_fills_by_row`). The table box in cell-text joining (`_join_soft_wraps`), the row list in column-boundary splitting (`_split_column_sections`) and the character list of the filtered page (`page_chars`) are computed only once — pdfplumber's `table.bbox`·`table.rows`·filtered-page `chars` are properties recomputed on every access | 3,000 filled cells took 4.1 seconds, 8,000 took 25.8 seconds, and 7,500 abutting filled bands took 68 seconds, growing with the square of the number of cells (inside a page, so the time budget cannot stop it either, round 42). After the fix a 7,500-cell page went from 24 seconds → 5.5 seconds and 7,500 bands from 70 seconds → 6.7 seconds; the rest is the page parsing time of pdfminer and pdfplumber | `test_pdf_resource_limits.py::TestManyCellsOnOnePage` |
| The cell index (`_BoxIndex`) does not put boxes taller than 128 bands (2,048pt) or with non-finite coordinates into bands; it keeps them aside and always scans them | A 1.6KB PDF with a ruled cell extending 30 million pt below the page created height/16 bands per cell and used 13.6GB and 17 seconds, and would not finish if longer (a regression of the round-42 index, round 43). Cells inside the page all go into bands, so the speed of the 7,500-cell page is unchanged | `test_pdf_resource_limits.py::TestCellsReachingFarOffThePage` |
| Finding line pieces to join (`_piece_joints`) keeps the piece start x values sorted per height band and picks only those within a space width by binary search (`_starts_between`) | It scanned integer x values one by one across the space width (font size × 0.35), so a 1.4KB PDF with a single character of size 1e9 never finished (a regression of the round-42 0.35em joining, round 43). Being inside a page, the time budget cannot stop it either | `test_pdf_resource_limits.py::TestHugeGlyphNextToOrdinaryText` |
| When a page with joined line pieces (`_rejoined_lines`) is grouped again, if the joined lines exceed `_MAX_GROUPED_TEXT_PIECES` they are grouped without text-box grouping (boxes_flow). Known accepted gap: the grouping on the first read is still used once if the pdfium estimate (`_survey_page`) is within the limit | A 20KB page (fuzzing) with a pdfium estimate within the limit but 2,098 pdfminer lines spent the quadratic time of text-box grouping twice and took 48 seconds (round 43). The estimate has to be made before pdfminer parses, so the first grouping does not know the line count | `test_pdf.py::TestLinesDrawnInPieces::test_page_with_more_lines_than_box_grouping_allows_is_not_grouped_twice` |
| The cell fill ratio (`_fill_cover`) stops adding the remaining fill rectangles once the cell is fully covered, and callers pass the widest rectangles first (`_by_area` — `_fills_by_row` per row, `shades` for shaded tables).
