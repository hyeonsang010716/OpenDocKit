# Legacy Word and PowerPoint (.doc, .ppt) decisions

Deliberate decisions of the LibreOffice bridge for Word and PowerPoint 97-2003 (`extractors/legacy.py`). The rule is the same as in [extractors.md](extractors.md): do not revert the decisions in this table. To change one, change its pinning test first and write the reason in the same row.

## Deliberate decisions (do not revert)

| Decision | Why | Pinned by |
| --- | --- | --- |
| `.doc` and `.ppt` are not parsed in Python. When LibreOffice is installed it is run headless to convert the file to DOCX / PPTX, and the result is read by `extract_docx` / `extract_pptx` unchanged, plus one warning that the document went through LibreOffice. `ConversionResult.format` stays DOC / PPT. Nothing else in the library uses LibreOffice | The binary formats are large and old; a second parser of our own would be worse than LibreOffice's and a permanent cost. The DOCX / PPTX extractors already hold every rendering decision, so the legacy formats inherit them. The warning tells the reader that lists, tables or notes are LibreOffice's reading of the file, not ours | `test_legacy.py::TestConversion::test_converted_docx_is_read_by_the_docx_extractor_and_reported_as_doc`, `test_converted_pptx_is_read_by_the_pptx_extractor_and_reported_as_ppt`, `test_options_reach_the_inner_extractor`, `TestRealLibreOffice::test_word_document_keeps_headings_lists_table_and_korean_text`, `test_presentation_keeps_slides_titles_levels_notes_and_table` |
| Without LibreOffice the file is an `UnsupportedFormatError` whose fixed message names the format, says it needs LibreOffice (with a one-phrase install hint) and offers saving as DOCX / PPTX instead. LibreOffice is not a dependency and is never downloaded | A default install stays pure Python and permissively licensed; the user learns in one message both ways out | `test_legacy.py::TestWithoutLibreOffice` |
| The program is `OPENDOCKIT_SOFFICE` when that variable is set, and nothing else is searched then: a value that is not a file means "not available" (no fall back to PATH), an empty value switches the bridge off. Otherwise `soffice` / `libreoffice` on `PATH`, then `/Applications/LibreOffice.app/Contents/MacOS/soffice`, the usual Linux `program/` folders and `%PROGRAMFILES%\LibreOffice\program\soffice.exe` (also the x86 folder). The search is cached per process (`reset_soffice_cache`); the variable is read on every call | An operator must be able to pin the exact program, or to guarantee that no subprocess is ever started. A mistyped override must not silently run another program. The search probes PATH and several folders, which is too much to repeat per upload | `test_legacy.py::TestLookup` |

See "What is and is not guaranteed" below | Measured with LibreOffice 26.2: with the default profile, converting a `.doc` whose picture is linked by URL sent `OPTIONS`, `HEAD` and `GET` to that URL — an address chosen by the uploader, requested from inside the server's network. | The time limit is the module constant `CONVERSION_TIMEOUT` (60 s), not an option. When it passes, the conversion is a `DocumentTooLargeError`. | Password protection is read from the container before LibreOffice is looked for: Word — the `fEncrypted` bit (0x0100) of the FIB flags at offset 10 of the `WordDocument` stream; PowerPoint — an `EncryptedSummary` stream, or the encrypted header token (0xF3D1C4DF) at offset 12 of the `Current User` stream. Stream names are compared case-insensitively, as in detection. A stream too short to hold the field, or a container that cannot be read, is not "encrypted" and goes on to LibreOffice. Known accepted gap: the fields follow [MS-DOC] / [MS-PPT] and are tested on built containers, not on files protected by Word or PowerPoint; a protected file that these checks miss ends as "LibreOffice could not convert the document" (or, if LibreOffice waits, as the timeout) | The same upload gets the same answer with and without LibreOffice ("remove the password", not "install LibreOffice"), and LibreOffice is not started on a file it can only fail on. The PowerPoint check uses the header token instead of searching the document stream for a `CryptSession10Container` record: one fixed offset instead of walking a record tree | `test_legacy.py::TestEncryption` |

## What is and is not guaranteed about macros and linked content

Guaranteed by this library:

- No shell, no file name of the uploader, and no content of the document in the command line; a private directory and profile per call; a time limit after which the whole process group is killed; no output or exit text in messages; the directory removed.
- The profile LibreOffice starts with asks for: macros disabled, no trusted macro location, links not updated, untrusted linked content blocked, HTTP and HTTPS sent to a proxy that does not exist.

Measured, on LibreOffice 26.2 (macOS): a picture linked by URL causes no request at all with this profile (it causes three with the default profile).

Not guaranteed:

- **Macros are disabled by configuration, not by a sandbox.** Whether a macro can run is decided by LibreOffice's own handling of those settings; `--convert-to` does not open a view and does not fire the document-open events, but this library cannot prove that no version of LibreOffice runs code from a document. `DisableMacrosExecution` exists since LibreOffice 7.0; older versions ignore it and rely on the security level. No test here runs a macro-carrying file.
- **LibreOffice's import filters are native code parsing untrusted input.** A memory-safety bug in them is outside what this library can prevent. The subprocess limits the damage to a separate process, but that process runs as the same user with the same file-system and network rights.
- **Other kinds of links** (OLE links, DDE, linked sections, `file://` targets, protocols other than HTTP / HTTPS) are covered only by the link settings, and were not measured one by one.
- **Memory** is not limited by the bridge. Under `IsolatedConverter` on Linux the worker's address-space limit is inherited by LibreOffice.
- **Windows**: the clean-up path (`taskkill /T`) is written but was not run on Windows, and there is no guard process there: a worker killed outright leaves LibreOffice and the temporary folder behind.

A service that accepts legacy files from the public should run the conversion in a container or sandbox without network access, keep LibreOffice patched, or switch the bridge off (`OPENDOCKIT_SOFFICE=`) and ask for DOCX / PPTX.

## Known accepted gaps

- Fidelity is LibreOffice's. Observed on the sample files: a slide-number field on the notes page comes back from LibreOffice as an ordinary text box, so the speaker notes of a converted `.ppt` end with a `> <number>` line (the PPTX extractor treats a text box on the notes page as notes); a chart may gain its series name as a title (`[Chart] 매출`).
- A date or time field that updates automatically ("today") is evaluated by LibreOffice when the file is converted, so its text is the conversion time and differs from run to run. Everything else in the output is stable.
- Every call pays a cold start of LibreOffice (about 2 s). There is no warm server process: a long-lived LibreOffice shared between documents would give up the per-call profile and the simple kill.
- Word 6 / 95 documents and PowerPoint 95 presentations are passed to LibreOffice like the 97-2003 ones (it chooses the import filter from the content); they were not tested.
