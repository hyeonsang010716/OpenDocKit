# PDF decisions: fonts

Decisions of the PDF extractor (`src/opendockit/extractors/pdf.py` and the `_pdf_*.py` modules beside it) about characters whose font information is incomplete (widths, encoding CMap) or whose font is a symbol font. Split off from [pdf.md](pdf.md) because of its size limit;
the rules are the same: do not revert the decisions in this table. To change one, change the pinning test first and write the reason in the same row.

## PDF fonts

| Decision | Why | Pinned by |
| --- | --- | --- |
| A page where half or more (`_UNMEASURED_RATIO`) of the visible characters have width 0 is read with pdfium plain extraction and a 'structure analysis failed' warning is issued (`_unmeasured`). The copy judgment (`_render_char_few_copies`·`_without_drawing_artifacts`) is not changed. Known accepted gap: that page comes out as line text only, without table or heading structure; and on a page where the zero-width font is less than half of the page's characters, characters of that font may still be lost as before | A font without /Widths for which pdfminer does not know the standard widths either (non-embedded TimesNewRomanPSMT, an embedded font that omitted /Widths) has an advance of 0, so the characters of a line pile up at the same x, and same-place copy removal erased real characters: '2024' became '204', 'report' became 'repot', and word spacing vanished too (round 36). Excluding only zero-width characters from the copy judgment would fail to block pages drawing fake bold or repeated text in the same font (the 110-second, 2.2GB case, pdf-limits.md). pdfium reads with the font's own widths. Standard fonts with known widths (Arial·Helvetica) stay with pdfminer | `test_pdf_fonts.py::TestFontWithoutWidths` |
| When a character of a symbol font (Symbol·Wingdings·Wingdings 2; the subset prefix, ',Bold' and '-Regular' in the font name are ignored; BaseFont if there is no font descriptor) comes out in the private use area (U+F020–F0FF), it is replaced at the moment it is drawn (`_render_char_few_copies` → `_symbol_font_glyph`) using that font's table (`_symbols.symbol_glyph`). Bullet code points (`_SYMBOL_BULLETS`) and code points not in the table are left as they are (the job of the shared mapping `markdown._SYMBOL_FONT_GLYPHS`). Pages with pdfium plain extraction do not know the font and are not replaced | Check boxes exported by Word (Wingdings 2 ☑ = F052·☐ = F0A3, Wingdings □ = F06F·☒ = F078) are code points missing from the shared mapping and were erased, so which of '동의 비동의' was marked vanished (round 36). The meaning of the same code point differs per font, so they cannot go into the shared mapping. The bullet judgment works on those PUA characters, so they are not touched | `test_pdf_fonts.py::TestSymbolFontCheckboxes` |
| The descent of a Type3 font is taken from the Descent of the font descriptor (FontDescriptor) (`_type3_font_with_descriptor_descent`, wrapping pdfminer `PDFType3Font.__init__`). It is used only when Descent lies between the bottom of the FontBBox and 0; a value outside that range which falls within it when divided by 1000 (only for fonts with a FontMatrix scale of 0.1 or more) is taken to be written in units of 1000. If there is no font descriptor, or Descent is 0 or broken, or neither case applies, the bottom of the FontBBox is used as pdfminer does | pdfminer takes the bottom of a Type3 character box from the bottom of the FontBBox. When LibreOffice exports a variable font ('Noto Sans KR'), only digits and periods are Type3 (FontBBox -1.05em, Descent -0.288em), so they sat 0.78em below characters of other fonts on the same baseline, splitting table cells into '0&lt;br&gt;배출량'·'Total&lt;br&gt;450' and paragraphs into '검 / . / 토' (round 43). Type3 font descriptor values are in glyph space units and so are scaled down by the FontMatrix as they are. Some generator writes Descent in units of 1000 (-288) for a font whose glyph space is text space (FontMatrix [1 0 0 1 0 0]); without the range check the descent became -288em and the digits went off the page and vanished without a warning (round 44) | `test_pdf_fonts.py::TestType3DigitsOnALine`, `test_pdf_round44.py::TestType3DescentInTheWrongUnit` |
| If the /Encoding of a CID font is a stream and pdfminer cannot find a predefined CMap by its CMapName, the tables inside the stream (cidchar·cidrange) are read (`_cmap_or_embedded`, wrapping pdfminer `PDFCIDFont.get_cmap_from_spec`; pdfminer unpacks cidchar pairs in reverse order, so `_EncodingCMapParser` reads them, and the range cap `_bounded_cmap_keyword` applies as is). If that font has a ToUnicode, the character code itself is used as the character number and the character widths (/W·/W2) are re-keyed to codes (`_cid_font_with_code_keyed_unicode`, wrapping `PDFCIDFont.__init__`) — ToUnicode maps by code but pdfminer looks up by CID. In a document where a font still could not be decoded, even a page with text left is read with pdfium, with a 'structure analysis failed' warning, if the pdfium plain-extraction character count exceeds 1.25 times the characters pdfminer read (`_read_chars`) + 10 characters (`_UNDECODED_TEXT_RATIO`). | WeasyPrint embeds the code → CID table for an OTF (CFF) Korean font (the Linux default Noto Sans CJK) as a `/WP-Encod-0` stream. pdfminer used an empty CMap, so 4,117 Hangul characters out of 4,476 in an exam-paper PDF vanished without a warning — characters of a Latin font on the same page kept it from taking the pdfium fallback for pages with 0 characters (round 48). Reading only the table erases characters whose code and CID differ as `(cid:n)`, and a fallback font without Hangul glyphs (DejaVu) sends hundreds of Hangul codes all to CID 0, so characters cannot be told apart by CID (a textbook PDF became '평평평'). The comparison is done only in documents with a font that could not be decoded — so as not to change normal pages where pdfium counts more, such as overdrawn copies | `test_pdf_round48.py::TestEmbeddedEncodingCMap` (including code ≠ CID and shared CID 0) |
| The estimate of the actual character width of separately placed text pieces (`_placement_fit`) accepts only 0.8 times (`_MIN_PLACED_ADVANCE`) to 0.95 times the font width (the lower bound used to be 0.5) | In a PowerPoint PDF that split words into a two-character + a one-character piece (character width equal to the font width, only 0.3em between words), piece lengths and boundary kinds interlocked so that 'width 0.67em, space 0.6em' fitted and a space was inserted at every piece boundary ('히스 토리', '상태 에 저장 된', round 48). The measured genuine case is 0.865em, and Hangul advancing less than 0.8x visibly overlaps its neighbours. The remaining conditions for restoring word spacing are in the separately-placed-text-pieces row of [pdf.md](pdf.md) | `test_pdf_round48.py::TestWordsSplitIntoTwoPiecesAtFullWidth`, `test_quality.py::test_pdf_words_placed_separately_without_space_characters_get_their_spaces_back` |
