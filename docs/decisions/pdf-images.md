# PDF decisions: picture placement

Decisions of the PDF extractor (`src/opendockit/extractors/pdf.py` and the `_pdf_*.py` modules beside it) about where pictures go: the box of a picture drawn clipped, pictures inside ruled table cells, the reading order of multi-column photo grids, and the reading order of text beside a picture and of picture captions.
Split off from [pdf.md](pdf.md) because of its size limit; the rules are the same: do not revert the decisions in this table. To change one, change the pinning test first and write the reason in the same row.

## PDF picture placement

| Decision | Why | Pinned by |
| --- | --- | --- |
| A picture's box is the part that overlaps the clipping area (`_figure_boxes`). Clipping that pdfminer and pdfplumber discard (`W`·`W*`, the BBox of a Form XObject) is followed by interpreting the content stream once more, only on pages with pictures (`_ClipInterpreter`·`_ClipRecorder`, together with q·Q). The clipping area is the rectangle enclosing the path points (including curve control points), so it is never smaller than the real area (conservative). Only records whose box equals a pdfplumber picture's box (within 0.5pt) are used — the recorded boxes and clips are first moved by the MediaBox's left edge, as pdfplumber moves x — and if interpretation fails nothing is clipped. The background judgment (`_covers_page`) and the scan judgment also use the clipped box | In PDFs that place a photo large and draw it clipped — browser `object-fit: cover`·`overflow: hidden`, cropping in office suites — the original placement box was cropped, so neighbouring body text got mixed into the picture, and if the original covered the page it was filtered out as background and the photo vanished without a warning. pdfminer is not patched globally; the stream is interpreted separately (only pages with pictures; total time over all 4,034 regression PDFs +4%). Besides the reproductions, 4 pictures changed (3 by a 1px difference, and 1 slide where two clipped photos used to cover the body text). In pdfminer's x, no clip matched its picture on a page whose MediaBox does not start at x = 0, and the clipping was silently lost | `test_pdf_images.py::TestClippedImages`, `test_audit_pdf_text.py::TestClipWithOffsetMediaBox` |
| A picture inside the box of one cell of a ruled table (2pt tolerance, `_CELL_IMAGE_SLACK`) is put in that cell, not after the table (`_place_images_in_cells`): in the cell whose box top and left ends match the start of a row range (`_Table.bands`) and a column range (`spans`), between the lines at the picture's height according to the top coordinates of the cell text lines (`cell_lines`, measured only for cells holding a picture) (at the end if the line count differs from the cell text). For a table with a carried header, a row range without a place is inserted at the top. Tables whose row and column ranges could not be derived, and borderless tables, keep pictures after the table as before | The cells of photo registers and product lists were left empty and the photos piled up after the table, so there was no telling which row a photo belonged to. The other formats put a placeholder inside the cell (assembly folds that row into one line). Putting it only at the end of the cell text sent the diagram in a '산정 로직' cell behind the source paragraph (a real review request form) | `test_pdf_images.py::TestPicturesInTableCells` |
| Three or more pictures (`_PICTURE_ROW_MIN`) placed side by side without horizontal overlap, with top and bottom ends at the same height (within 2.5pt), are seen as one row (`_picture_rows`): only the first (leftmost) picture of the row looks for its place and the rest are put right after it in left-to-right order. Two side-by-side pictures are handled as before (they may be pictures of two columns) | In photo grids of 4 or more columns (product guides, product line-ups) the caption below a photo is wider than half the photo width and looked like 'body text of another column' (`_in_other_column`) for the neighbouring photo, so photos and captions were mixed up. 2- and 3-column grids were read as 'photos → captions' per row, and this was matched. Among the regression PDFs only the 6 reproductions (4·5·6-column grids) changed | `test_pdf_images.py::TestPictureGrid` |
| In lifting pushed-down lines (`_read_lone_lines_in_place`, [pdf-rows.md](pdf-rows.md)) the line to move may have **only a picture** beside it (if a line or table is beside it, it is not moved, as before). A caption line right below a picture (gap ≤ line height) and within the picture's horizontal range (`_is_figure_caption`) also skips lines to skip that have lines beside them (a row of side-by-side cards). The one-column flow judgment (`_one_flow`) is unchanged. The place of a picture moved to another column (`_position_in_column`), when there is no same-column paragraph above it, is before the **topmost** same-column paragraph, not the first one in reading order. Known accepted gap: text on the right that starts just over 1pt above a picture comes before that picture (the second photo of a site report comes after the '2구역' text) | In a layout with the picture on the left and text on the right (a Chrome site report), pdfminer first read the subheadings and the first table column in the left margin as one column, so the text to the right of the picture was pushed behind the subheading and table below (to the end of the page for a clipped picture) — it was not moved because a picture was beside it. A slide's picture caption was pushed behind the row of side-by-side cards below it, and the picture was wedged in at the first same-column paragraph in reading order (a card), ending up between the cards. A right-column line beside a picture on a two-column page stays as is through the condition of vertical overlap on both sides of the gap (`_one_flow`). Of 52 reproduction PDFs only the 5 with text beside a picture changed | `test_pdf_pictures_beside_text.py::TestTextBesideAPicture`, `TestCaptionUnderAPictureBesideText` |
| No picture of a PDF is drawn (and a warning counts them) when the document holds a JPEG 2000 picture that would stop pdfium (`_pdf_jpx.stops_the_renderer`, asked by `_PageRenderer.render` the first time a picture is to be drawn). The rules follow pdfium 159's code. A picture stops it when the colour space pdfium takes for it asks for more components than the picture decodes to: any space but the stock DeviceGray and DeviceRGB (pdfium refuses an RGB picture of fewer than three), and the stock DeviceCMYK over three components unless the picture names another space; a stock device space stands for the default space the resources give for it (DefaultGray, DefaultRGB, DefaultCMYK — one of ICC profiles keeps the device's components when the picture names the device), a name not stock for the space the resources give under it, an array for its family by the first four letters of its first name (so an array that starts with DeviceRGB and lists four names is DeviceN); with no colour space, a picture whose first JP2 colour box names CMYK over three components. An image mask stops it when pdfium takes its picture for gray (one or two components, or a gray colour box). The components are those openjpeg decodes: a palette's columns when a component map comes with it. Every stream pdfium decodes with JPXDecode counts (its Filter as pdfium reads it: resolved, and only Flate, LZW, ASCII85, ASCIIHex or RunLength before it), wherever it is drawn from; an inline picture is not decoded by pdfium, and an object the cross-reference table does not name is drawn by nothing. A picture whose header or data cannot be read counts as one that stops it, and so does a document of more than 50,000 JPXDecode names or 200,000 objects. A file whose bytes name no JPXDecode (also written with `#hh`) costs only that search; one that does is read as little as it can be — the object each name is read in, its object streams, and every object only when a name is in no picture or a space is looked up in resources. Known accepted gaps: the pictures of the whole document are lost, not only those of a page; a filter written only in an object stream of a file whose bytes name no JPXDecode is not looked for (inflating the object streams of every PDF with pictures cost 2.6 s on one of 343 such PDF.js test files); a broken cross-reference table that defines an object twice is read as pdfminer reads it, which can differ from pdfium; a colour space written as null is read as none, and pdfium then draws nothing where the guard judges the picture's own space; a document of more than 200,000 objects whose resources must be read (a default space, a space named there) loses its pictures; a file made to stop pdfium can find other ways — a server converts in `IsolatedConverter` ([../server.md](../server.md)) | A check of pdfium, not an error it returns, ends the process (`CJPX_Decoder::Decode`: `CHECK_LE(component_count, image_->numcomps)`, SIGTRAP; on x86 SIGILL), and for an image mask taken for gray libc++ ends it reading past the end of a list (`CPDF_DIB::LoadPalette` reads `comp_data_[0]` of an empty vector, SIGABRT): the PDF.js test file `jpx_numcomps.pdf` (10 KB, six pictures, one a DeviceN of four colorants over two components) ended every program that converted it in its own process, a server with it. pdfium's main branch has the same check, and pypdfium2 5.15.2 is the newest. Each rule was measured on a picture built for it and drawn by pdfium 159 in a process of its own: the 79 cases of the tests agree with it, and of 59 more built by a review 58 (the one left: an object defined twice in a broken table). A first version found default spaces only in the file's bytes, not in object streams, and took a stock name for its device space whatever default the resources gave; looked for each name's object back to the start of the file (a stream holding a name every 100 bytes took a minute for a megabyte, now 0.04 s); read pdfminer's filters, which take an F entry for them; and counted a picture nothing draws. A second review found the default spaces read again for every picture over every resource dictionary: a scan of 3,000 pages that each name DefaultGray took 12 s, the square of its pages; each name is read once per document now (0.5 s). On 1,959 other PDFs, 16 of them with JPEG 2000 pictures, it stops none that pdfium draws (it counts one: a file under a password that neither pdfium nor pdfminer opens), and no text changes | `test_pdf_jpx.py::TestTheRendererStops`, `::TestWhatIsNotJudged`, `::TestTheObjectOfAName`, `::TestCost` |
