# PDF decisions: ruled-table cell text, highlights and shaded tables

Decisions of the PDF extractor (`src/opendockit/extractors/pdf.py`) about joining lines of text in ruled table cells, filtering out highlighter marks before table finding, and tables made of cell shading (stripes, header shading). Split off from [pdf-tables.md](pdf-tables.md) because of its size limit;
the rules are the same: do not revert the decisions in this table. To change one, change the pinning test first and write the reason in the same row. Overflowed lines (`<br>`) in borderless table cells are
decisions of [pdf.md](pdf.md)·[pdf-borderless.md](pdf-borderless.md) and are not changed here.

## PDF ruled-table cell text

| Decision | Why | Pinned by |
| --- | --- | --- |
| Before the characters of ruled table cells are read, a space character (a space that does not advance) is removed when the very next character in drawing order starts, on the same line, before the space's start point and covers that start point (`_without_unadvanced_spaces`, only on the page used for table finding — body lines are untouched). Word spacing is decided again by the cell character gaps (`_CELL_TEXT`) | A document with tightened character spacing draws a space and then draws the next character before the space's start point. pdfplumber lays out cell characters in x order, so the space ended up after the first character of the next word, giving '•새 로운'·'측 정원리' (25 places in one manual). Deciding by overlap width (half the space or more) removed ordinary spaces of Latin fonts whose character box is wider than the advance, turning 'CI / CD' into 'CI /CD' | `test_quality.py::test_pdf_table_cell_space_drawn_under_the_next_letter_does_not_split_the_word`, `test_pdf_table_cell_space_overlapped_by_a_letter_that_still_advances_is_kept` |
| Among the lines of a ruled table cell (`_cell_rows` → `_join_soft_wraps`), a line that wrapped because of the cell width is joined with a space: the cell is left-aligned (first-line indent allowed), the next line has the same size and does not start with a list number or bullet (`_BARE_LIST_NUMBER`·`_BULLET_START`), and the first word of the next line plus a space would not fit between the end of this line and the right end of the cell (minus the left cell padding) (`_soft_wrapped`). A cell with a single Hangul/Hanja character on every line is joined without spaces ('인/적/사/항' → '인적사항'). A cell containing a picture, a cell containing rotated characters, a cell whose lines regrouped from characters do not match the cell text lines, and centre- or right-aligned cells keep `<br>` per line as before. Deliberate: generators that wrap Hangul per character (wrapping in the middle of a word) are joined with a space too | Cell text was broken with `<br>` at every visual line, so one cell of an old/new provisions comparison table became '…임직원이 업무를<br>수행함에…' and each line added the four characters of `<br>` to the character count (round 36). Whether a line break is mid-word cannot be known; in that case '수 행함에' is broken just as much as the former '수<br>행함에', and with the word-wise wrapping that is the default in Word and Hangul (HWP) it is the original text as is. In a centred cell ('위와 같이 … / 날짜 / 신청인' at the end of an application form) the breaks are real line breaks even when, measured against the widest line, there seems to be no room. The place of a picture is determined by the height of the cell text lines (`_place_images_in_cells`) | `test_pdf_cell_wraps.py::TestSoftWrappedLinesInRuledCells` |

## Highlights and filled cells

| Decision | Why | Pinned by |
| --- | --- | --- |
| Highlighter rectangles are removed before table finding (`_without_highlights`): filled without a border, covering one line of text, at most twice the font size high, left end aligned with the first character and right end right after the last character. An abutting rectangle without text is removed along with it only when it has **the same fill colour** as the highlight. Kept: a rectangle with the same left and right ends as one in another row but different text (cell shading aligned to columns), and rectangles of which there are two or more on a line and all of which line up in columns (left, right or centre) with **unfilled** words within 6 lines above or below (`_without_cell_rows`, a filled header row). Characters are aligned by vertical centre and only those within the rectangle's height are chosen. Known accepted gap: a filled row whose columns do not line up with other rows is removed as a highlight. A filled header row + borderless data rows come out as two tables regardless of highlights | A LibreOffice highlighted paragraph became a table with a cell per word (round 39). Without looking at the colour, the neighbouring vertical rules that Chrome draws as filled rectangles were removed too and a row became one cell ('\| 사과 확인 필요 입고 \| \| \|'), and a Chrome filled header cell fitting its text was removed as a highlight so the header became a paragraph outside the table. Checking columns among filled words turned highlighted lines repeating the same text into a table. Choosing by a band twice the largest character on the page took 10 seconds on a page with one large character + 40,000 filled rectangles (round 40) | `test_pdf_highlights.py` (`TestChromeTables`, `test_many_painted_squares_beside_one_huge_letter_take_linear_time`) |
| The evidence for column shading (a rectangle with the same left and right ends in another row) is only a cell that fills its row without gaps: a rectangle that abuts the neighbouring cell shading with equal top and bottom ends and has no unfilled text on the same line. A filled table row (`_without_cell_rows`) groups lines by the rectangles' centre height, and only when that line has no unfilled word, the candidates have equal top and bottom ends and abut each other (`_tiled_row`). Known accepted gap: a shaded table with only one column filled, or a font-change line filled as one run (abutting runs with equal top and bottom ends), remains if it happens to line up in columns with text of another row | Looking only at column alignment, the first candidate on a line matched the left margin and the second matched one of dozens of surrounding words within 1pt by chance, so a Chrome·LibreOffice paragraph with a few filled words became a fake table '\| 중소기업 \| 10월 \|' and the filled words dropped out of the sentence (round 40 regression). Hangul characters have equal widths, so highlights on '고 '·'다 ' at line starts and '장비'·'홍보' filled in each cell of a ruled table had equal left and right ends and remained as column shading, and the highlight sides became vertical rules, shifting columns as in '\| \| 장비 \| 150 \|'. Grouping lines by the top of the characters put Hangul and digit runs on different lines, so paragraph lines repeating the same text looked like cell rows (round 41) | `test_pdf_highlights.py::TestScatteredHighlightsInAParagraph`, `TestChromeTables` |

## Tables made of cell shading

| Decision | Why | Pinned by |
| --- | --- | --- |
| A ruled table in which cell shading (rectangles filled without a border, both sides over 2pt `_SHADE_MIN_SIDE`, white excluded) covers 60% or more of the cells is searched again after widening it band by band with the same column boundaries (`_with_shaded_rows`·`_grown_shaded_table`): above and below, another table fragment with the same column boundaries, a horizontal rule covering the table width, or, if neither exists, a single open band as high as the fragment's row height (only when the text beyond it is more than half a row height away, `_ends_the_text`). For a band and for a merged-cell row inside the table, vertical lines at the column boundaries are added to the band only when the text is in two or more columns, does not spill outside the band or the table, does not cross a column boundary at a word gap (less than 0.5 times the font size `_CELL_GAP_MIN_RATIO`) (`_band_cells`), and two or more columns match the same-column text of another row in left edge, right edge or centre (`_aligned_cells`). A character that reaches into the band by less than 0.3 times the character height (`_BAND_SLACK_RATIO`) is the neighbouring row's text and is not counted. If the topmost closed band has text in every column and no numeric cell (`_is_header_band`), it is accepted as the header without alignment. If even one band between filled fragments does not fit, nothing is changed. Only that area is searched again and it is replaced only when the result is one table with the same number of columns. If, after widening, the shaded fragment with the most column boundaries and a fragment with only a subset of those boundaries (front columns missing because of a vertically merged cell) remain within 1.5 row heights, the area covering both is divided again by the column boundaries of the wide fragment (`_with_merged_column_fragments`, round 33): row boundaries are the row boundaries of the fragments and the sides of filled rectangles, and horizontal lines go, per column, only at boundaries that the column's text does not straddle by more than 0.15 times the line height (`_MERGED_TEXT_CROSSING`) and that are not inside a filled rectangle. Fragments with the same column boundaries are not touched. Known accepted gap: the continuation stops at an unfilled row with text in only one column (a section row); only one open band each above and below (exception: the unfilled first row + header of the round-44 row below); an unfilled merged cell that does not straddle a row boundary (the middle of an odd number of rows) is split per row | pdfplumber uses the sides of filled rectangles as rules, so in a striped table filled cell by cell (Chrome `tr:nth-child(even)`, Word 'Light Shading') only the filled rows became ruled tables and the unfilled rows became separate paragraphs, shuffling the row order and scattering the numbers (including a 1,200-row table). In a table with only header cells filled (Chrome th background + bottom border per row, LibreOffice) only the header was a table and the first data row became the header. In Word 'Medium Shading 1'·'Light List', whose vertical lines exist only in the header row, the unfilled rows were merged into one cell. Left-aligned text of an unfilled header did not align with right-aligned numeric columns, so widening was given up wholesale (Word 'Light Shading', Chrome stripes), and the character box of a Word numeric column touched the band of the row below by 0.06pt, so that band was rejected and the unfilled rows were merged into one cell (round 32). Removing filled rectangles from the rules breaks thin borders drawn as fills (Chrome 0.7pt) and tables closed by filled cells. Without the alignment condition, body text and first-column notes below a filled header became table rows, and without the open-band condition, the first line of a list below side-by-side filled title boxes did. Of 52 reproduction PDFs only the 7 shaded tables changed; the cell-mark judgment (■, Gantt) is unchanged. A rowspan cell of a striped table takes the fill of its starting row, so 4-column and 3-column fragments became separate tables, and the widened 3-column table overlapped the 4-column fragment so rows appeared twice or '2팀'·'개발팀' dropped out (round 33). Known accepted gap: if the page text is almost only a table, the body size (`_body_font_size`, ruled table cell characters not counted) is taken to be the table title's size and `# 표 제목` (the table title heading) drops to an ordinary paragraph (the text remains) | `test_pdf_shaded_tables.py::TestShadedTables` (round 32: `test_unshaded_header_over_banded_rows_with_right_aligned_numbers_stays_one_table`, `test_numbers_that_barely_touch_the_next_row_do_not_merge_its_cells`), `TestShadedTablesWithMergedCells` |
| If the cell boxes of a shaded table found only from the sides of filled rectangles do not cover the whole table box (`_has_holes`, under 98%), it is divided again by the column boundaries of the wide fragment even if there is only one fragment (`_with_merged_column_fragments` → `_regridded_fragments`). The row height used for widening and re-dividing shaded tables is the median distance between the top and bottom sides of cell boxes (`_row_pitch`) — not the pdfplumber row box height | When every vertically merged group of a striped table starts on a filled row (Chrome `tr:nth-child(even)` + rowspan 2·3), the filled rectangles join into one table and the unfilled rows from the second column on were left as holes; with no separate wide and narrow fragments it was not re-divided, and those rows were scattered outside the table one number at a time (round 44). With the row height measured from rows spanned by a merged cell (two or three rows), the last open band covered the paragraph below the table ('개발본부5&lt;br&gt;끝.') and the header band covered the caption above the table ('표 2. 본부별&lt;br&gt;구분') | `test_pdf_round44.py::TestZebraTableWhoseMergedGroupsStartOnShadedRows` |
| When the open band above the topmost filled fragment of a table (an unfilled first data row) cannot be accepted because it continues into the text above at line spacing, if the one-row-high band above it is header-shaped (`_is_header_band`) and the text above that is set apart, the two bands are accepted together as the open band (`_unshaded_head`; the alignment condition `_aligned_cells` is unchanged) | In a striped table with neither the header nor the first data row filled (Chrome `tbody tr:nth-child(even)`) the header was scattered as '번호 지점 / 금액 / 상태' and the first row became a jumbled paragraph — worse than without any fill. A 2,500-row table lost the first row on every odd page, 28 rows in all (round 44). A line with a numeric cell is not accepted as a header | `test_pdf_round44.py::TestZebraTableUnderAnUnshadedHeaderAndFirstRow` |
