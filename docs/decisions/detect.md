# Format detection decisions

Deliberate decisions of format detection (`detect.py`, plus `extractors/html.is_mhtml` and `extractors/text.mime_mail` / `mail_box`, which detection uses).
Split off from the common decision table in [core.md](core.md). The rule is the same: do not revert the decisions in this table. To change one, change its pinning test
first and write the reason in the same row. Reading mail bodies (forwarded mail, attachments, mbox, meeting invitations) is in [mail.md](mail.md).

## Deliberate decisions (do not revert)

| Decision | Why | Pinned by |
| --- | --- | --- |
| PDF detection is `%PDF-` at the very start, or `%PDF-` within the first 1 KB + body structure (`startxref`, `N N obj`). When a file whose header is not at the very start cannot be read as a PDF (corrupted, parser exception) and the whole file is UTF-8 text, it is read again as the text family (`converter._extract`, `detect.pdf_lookalike_text_format`). This is not decided at detection time — telling it from a real PDF with text in front requires reading it. Known accepted gap: CP949 notes are not rescued this way, and when only `detect_format` is called such a note is a PDF too | Anything with the header was taken for a PDF, so a note explaining the PDF format was rejected as a 'corrupted PDF'. So was a note that also wrote out the structure keywords. A PDF with junk bytes in front is still accepted, and a binary PDF does not decode as UTF-8, so corrupted stays corrupted | `test_detect.py::test_text_that_mentions_the_pdf_header_is_not_a_pdf`, `test_pdf_with_leading_junk_is_still_a_pdf`, `TestTextThatLooksLikeAPdf` |
| Format detection and the ZIP check are inside the same exception boundary as extraction | An encrypted ZIP (RuntimeError) and an unknown compression method (NotImplementedError) leaked out past ConversionError | `test_converter.py::test_zip_that_cannot_be_inspected_is_a_conversion_error` |
| ZIP detection decompresses only the front of the parts (mimetype, `_rels/.rels`) (`detect._read_prefix`; `archive.read` is forbidden). The zip-bomb check (`_guard_zip`) still runs after detection | Decompressing whole and then slicing made a 1 MB file use 2.1 GB before the bomb check | `test_detect.py::TestZipDetectionMemory` |
| Excel 2003 XML is singled out before HTML detection and read as sheets (`XML_SPREADSHEET`); when the XML parser rejects it, it is decoded with decode_text and parsed again | `<Table>` was detected as HTML and gave an empty result; leading blank lines of JSP/ASP output and CP949 caused rejection | `test_detect.py::test_detects_excel_2003_xml_spreadsheet_instead_of_html`, `test_office.py::TestXmlSpreadsheet` |
| OOXML detection uses the fixed names first, then the folder of the officeDocument target in `_rels/.rels` (the XLSX resource check uses the same part). The 64 KB extension of HTML detection applies only to documents that start with a tag (including `<tr>`, `<td>`) | A document with `word/document2.xml` was rejected, and an '.xls' export whose table follows a long `<style>` became text. A note that starts with prose is not taken for HTML | `test_detect.py::TestRenamedMainPart`, `test_detects_html_export_with_long_preamble_or_bare_rows`, `test_text_that_mentions_a_table_tag_late_is_still_text` |
| A package whose main part is `xl/*.bin` (.xlsb) is an `UnsupportedFormatError` at detection time | It went on as XLSX and was rejected as a 'corrupted document', with no advice to save it again | `test_detect.py::test_binary_workbook_is_reported_as_unsupported_not_corrupted` |
| RTF (`{\rtf`) is detected by content and read by the RTF extractor (it used to pass as text, then to be rejected; `test_detect.py::test_rtf_is_read_as_rtf_whatever_the_extension`). SVG (top element `<svg>`, when the extension is not a text one) is `UnsupportedFormatError`. The same goes, when the extension is not a text one, for Word XML (processing instruction progid="Word.Document" or top element w:wordDocument), single-XML ODF (top element office:document; fodt, fods, fodp) and Hangul XML (top element HWPML, .hml) | Being formats made of characters, they passed as text and control words, path coordinates and XML tags became a 'successful' result. HWPML was read as HTML: tables were scattered and base64 became body text | `test_detect.py::test_svg_is_reported_as_unsupported_instead_of_passing_as_text`, `TestOtherXmlDocuments`, `TestHwpml` |
| Text with the extension `.xls` is CSV when its first 20 lines all contain a tab or all have the same number of comma/semicolon cells (`csv.reader`, excluding inside quotes; 2 or more cells) (`detect._looks_delimited`). Up to 5 leading title or query-condition lines of at most 100 characters are set aside, but then at least 3 remaining lines and 3 cells (2 tabs) are required. Only after HTML, MHTML and XML detection | TSV/CSV 'Excel downloads' were read as text and did not become tables (also those with title lines attached). Counting the comma in `"1,200"` missed a CSV. Two-cell note lines are not CSV | `test_detect.py::TestDelimitedTextServedAsXls`, `TestDelimitedTextWithTitleLinesServedAsXls`, `test_comma_inside_quoted_value_does_not_hide_a_csv_served_as_xls` |
| MHTML (single-file web page) is detected by its header structure (MIME-Version + a multipart/related or text/html Content-Type in the leading header block) and read as HTML. The transfer encoding of the first text/html part is decoded and the part's charset is used as the declared charset. Without an HTML part it is an `UnsupportedFormatError`. MHTML with a text extension (.txt, .md) is text, headers included. Mail whose leading header block has MIME-Version and a mail Content-Type (a multipart other than multipart/related, or text/plain) (`text.mime_mail` — .eml, and .mht of the same structure) is, regardless of the parts' transfer encoding (base64, quoted-printable, 7bit, 8bit), HTML when it has an HTML body part (attachments excluded, `html.mail_html_parts`) (cid pictures included), and decoded text when it has only plain-text parts (also for .txt). Both put Subject, From, To, Cc and Date first with RFC 2047 decoded, discard MIME headers and boundaries, and warn about attachments with names and count only (forwarded mail, attachment verdicts, mbox and meeting invitations are in [mail.md](mail.md)). A message detected as MHTML also gets mail headers when it has recipients (To, Cc) or its sender is not `<Saved by …>` (the browser's save mark) (`text.is_sent_mail` — single-part text/html mail, multipart/related mail with embedded photos). Known accepted gap: only the first part is read (the parts of later sheets in a multi-sheet Excel MHTML are not read; when the body seems to be in a frame part there is only a warning — [html.md](html.md)) | MHTML that groupware and ERP systems hand out as .xls/.doc passed as text, and MIME headers, base64 and `=C7=B0` became a 'successful' result. A saved .eml (body base64, or body 8bit with base64 attachments — Thunderbird's default) was also a 'successful' result with the base64 as is. Single-part text/html mail was read as MHTML and lost its subject and date. 7bit/8bit mail (Thunderbird default, Gmail ASCII) stayed 'readable plain mail', so MIME boundaries and part headers became the result, `=?utf-8?b?…?=` subjects were not decoded and multipart/alternative bodies came out twice (the earlier decision 'plain mail is text, headers included' was changed with the owner's approval) | `test_detect.py::TestMhtml`, `test_text_html.py::TestMhtml`, `TestEncodedMail`, `test_core_mail_and_detect.py::TestSinglePartHtmlMail`, `TestPlainMailWithAnEncodedAttachment`, `TestMailWithoutTransferEncoding` |
| A document that starts with prose is not HTML on the strength of opening tags in the first 2 KB alone; there must also be closing tags (`</table>`, `</tr>`, `</td>`, `</html>`, `</body>`, `</p>`, `</div>` etc.) within 64 KB. A document that starts with a tag is HTML even unclosed. Code, data, config and log extensions (`detect._CODE_EXTENSIONS` — .json, .py, .js, .yaml, .log etc.; server scripts .jsp, .php, .asp excluded) and `{`/`[` text that parses as JSON (first line for JSON Lines) are text before HTML detection. Known accepted gap: unnamed code can still be HTML | A log that wrote a tag name once (.log, .json, unnamed) was read as HTML: lines were squashed and the text after the tag was lost. An HTML export that follows a title line or server warning is still HTML. JSON and code holding an HTML string (closing tags included) as a value were read as HTML and keys and indentation were squashed | `test_detect.py::test_prose_that_only_mentions_an_html_tag_is_text`, `test_html_that_starts_with_a_little_prose_or_is_not_closed_is_still_html`, `test_core_mail_and_detect.py::TestHtmlInsideJsonAndCode` |
| Extension warnings: a text extension gives no warning among text formats (exception: a `.csv`/`.tsv` holding an HTML table is HTML + a warning — [csv.md](csv.md)), but a warning for a binary document. Every image extension is a claim | An XLS inside `.csv` and a PDF inside `.gif` were read without a warning | `test_detect.py::TestExtensionMismatchClaims` |
| OLE stream names (`Workbook`, `Book`, `EncryptedPackage`, `WordDocument` etc.; HWP excluded) are case-insensitive. A BIFF record stream without OLE is XLS too (`detect._is_raw_biff`, conservative — BOF type, length and substream type of the first record + the record chain up to EOF) | An XLS with a `WORKBOOK` stream, an encrypted docx with `ENCRYPTEDPACKAGE` and a PHP 'Excel download' were rejected as an 'unsupported format' | `test_detect.py::TestXlsStreamNameCase`, `TestOleStreamNameCaseForOtherDocuments`, `TestRawBiffWithoutOle` |
| Reinforced mail detection: (1) with two or more mbox separator lines + header blocks, the file is split as a mailbox even when the first mail does not pass mail detection (single-part text/html, multipart/related, old mail without MIME headers), and both detection and HTML extraction look at this before MHTML (`text.mail_box`). (2) Even without MIME-Version it is mail when From + one of To/Subject/Date + a MIME body header (a mail Content-Type — including related and text/html — or Content-Transfer-Encoding) are all present (`text._mail_without_mime_version`). A note starting with `From:`, `To:`, `Subject:` has no body header and is prose. (3) Mail whose top level is S/MIME encrypted (application/pkcs7-mime, excluding signed-data and certs-only) or PGP/MIME (multipart/encrypted) is an `EncryptedDocumentError` (`text.is_encrypted_mail`, text extensions excluded). Mail that is only signed is read as usual. (4) Mail with nothing to read as HTML (MHTML excluded) is text even when named `.html`/`.htm` (`detect._is_plain_mail`) | (1) When the first mail was HTML the later mails were appended to the first body as raw text, and with related they disappeared. (2) Mail that omitted MIME-Version was text with its encoded subject and base64 body as is. (3) S/MIME encrypted mail was a 'successful' result of headers + base64 ciphertext; of PGP only the headers were left. (4) Plain mail went to the HTML extractor and headers and body were squashed into one line | `test_core_mailboxes_and_charsets.py::TestMailboxThatStartsWithAnHtmlMail`, `TestMailWithoutMimeVersion`, `TestEncryptedMail`, `TestPlainMailNamedAsHtml` |
| The KS X 1001 8-byte filler sequences in text decoded as CP949 (filler U+3164 + initial, medial and final jamo) are composed into one syllable (`text._with_filler_syllables`; left alone when the initial or medial is missing). Known accepted gap: UTF-16 text without a BOM, null bytes or any ASCII (a few Hangul characters with no space or line break) is not taken for UTF-16 — whether pairs of bytes decode to Hangul syllables is no basis for telling it from CP949 extended Hangul or other double-byte text | A syllable missing from the precomposed set ('똠') decoded into four jamo ('ㅤㄸㅗㅁ'). With even one space or line break, UTF-16 is recognized by its null bytes, so this is rare in real files | `test_core_th_rows_front_tables_and_linear_time.py::TestEucKrFillerSyllables` |
