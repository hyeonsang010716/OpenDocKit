# Integration decisions (LangChain, LlamaIndex, MCP)

Deliberate decisions of `opendockit.integrations` and `opendockit.mcp_server`. The rule is the same as in [extractors.md](extractors.md): do not revert the decisions in this table. To change one, change its pinning test first and write the reason here.

| Decision | Why | Pinned by |
| --- | --- | --- |
| The adapters live in this package behind extras (`langchain`, `llamaindex`, `mcp`), not in separate distributions. Nothing in `opendockit` imports them. Each adapter module fails on import with the install command when its framework is missing; `mcp_server` imports without the SDK, because its command is installed for everyone, and says the same when it is started | One version, one release and one test run cover the converter and its adapters; a separate package per framework would be three more things to keep in step for about fifty lines each. The price: the adapters are not named the way the frameworks' own catalogues expect (`langchain-…`, `llama-index-readers-…`) | `test_integrations.py`, `test_mcp_server.py` (skipped when the extra is missing) |
| One exception to "no separate distributions": `opendockit-mcp` on PyPI (`packages/opendockit-mcp`) — a launcher with no module, the same version, one dependency (`opendockit[mcp]==` that version) and the same console script. It is built and published by the same release run, followed by the entry in the MCP Registry (`server.json`) | The MCP Registry, and the clients and catalogues that read it, start a server as `uvx <package name>`: they cannot say "the `mcp` extra of `opendockit`, and a command named differently". Entries that try (`--from pkg[mcp]` as a runtime argument) depend on each client honouring it. The reasons against separate packages do not apply to this one: there is no code to keep in step, and a test compares its version, pin and entry point with this package's. Price: when both are installed, uninstalling the launcher removes the `opendockit-mcp` script until `opendockit` is reinstalled | `test_mcp_launcher.py` |
| One function (`integrations._documents.pieces`) decides how a result is cut and what its metadata is, for every adapter | An index built with LangChain and one built with LlamaIndex must cite the same page for the same passage | `test_integrations.py::TestLlamaIndexReader::test_load_data_gives_documents_with_the_same_pieces_as_the_loader` |
| `mode="sections"` gives one piece per page, slide or sheet; a document without physical units is one piece in either mode. The adapters do not split by headings or by size | Pages, slides and sheets are facts of the file and the unit people cite. How to chunk prose is the caller's choice, and the frameworks already have Markdown splitters | `TestLangChainLoader::test_sections_mode_gives_a_document_per_sheet_slide_and_page`, `test_document_without_units_is_one_piece_in_either_mode` |

When `sections` finds nothing in the range asked for, the MCP server names the numbers that exist | A deck of divider slides came out empty in `sections` mode. A 20-slide deck cut after slide 16 gave title pieces for slides 17-20, which the text never reaches. Numbers can have gaps (an empty first sheet), so 'the document has 1 sheet' sent the agent back to sheet 1 | `test_integrations.py::TestLangChainLoader::test_slide_that_is_only_a_title_is_kept`, `test_sections_past_the_character_limit_give_no_piece`, `test_mcp_server.py::TestConvertDocument::test_note_names_the_numbers_that_exist` |
| A result with no text to hand on gives no document, and one warning with the path and the converter's warnings is logged (`opendockit.integrations`). Bare placeholders for content that was not read (`[Image]` with no alt text or description; `[Chart]`, `[Video]` and `[OLE object]` with nothing after them), the bare cell before a sheet picture (`(cell C2)`; `(cell C2: 제품A)` carries the text of its row and is kept) and page markers are not text to hand on, and neither is the `## Sheet:` heading of a piece (a slide that is only a title is kept, row above). Known accepted gap: a text or Markdown file whose typed text is nothing but such placeholders (`[Image]`) gives no document either | An empty Document breaks embedding calls, a Document holding only `<!-- Page 1 -->` markers is noise in the index, and so was one of `[Image]` for a picture file read without a describer, or one of `## Sheet: Photos` and `(cell C2)` / `[Image]` lines for a sheet of pictures, and no Document at all is silent: a scanned PDF would vanish from the index without a word. The warnings have no Document to travel on | `TestLangChainLoader::test_file_without_any_text_gives_no_document_and_a_logged_warning`, `test_pictures_without_a_description_give_no_document`, `test_sheet_of_pictures_gives_no_document`, `test_what_says_nothing_on_its_own` |
| `OpenDocKitReader` reads through the fsspec file system `SimpleDirectoryReader` hands it (`fs=`), and implements `lazy_load_data` | Ignoring `fs` read the local disk for a file that lives in a bucket; the directory reader printed an error and skipped it | `TestLlamaIndexReader::test_file_system_given_by_the_directory_reader_is_used`, `test_lazy_loading_gives_the_same_documents` |

Fresh lists per Document, which `SimpleDirectoryReader` extends with its own keys | LlamaIndex writes every metadata value in front of each node: a workbook with 80 hidden sheets had 5,269 characters of warnings in every node, and `SentenceSplitter(chunk_size=1024)` refused it ('Metadata length (1132) is longer than chunk size'). An answer lists at most 20 warnings and counts the rest; the outline lists pages, slides or sheets as far as the server's `--max-chars` and counts the rest with their numbers | The agent's context is the scarce resource: a 400-page PDF returned whole fills it and the conversation is over. The converter's own 'stopped' warning is dropped from the answer because the note already says it. A workbook of 400 hidden sheets put 25,000 characters of warnings under a 200-character answer, and one of 3,000 sheets gave an outline of 173,000 characters | `test_mcp_server.py::TestConvertDocument::test_long_document_is_cut_at_max_chars_with_a_note_saying_how_to_read_the_rest`, `test_sections_selects_pages_by_number_or_range`, `test_warnings_of_an_answer_are_bounded`, `TestDocumentOutline` (`test_outline_of_many_units_stays_within_max_chars`) |
| The note under a cut answer and the outline say what can reach the rest. With pages, slides or sheets: the outline and `sections`, or a larger `max_chars`. Without them (a DOCX, an HTML page) only a larger `max_chars`: the note says to raise it, and the outline of a text longer than the server's default `max_chars` says that `convert_document` returns its first characters, not the whole of it | A 292,888-character DOCX was cut with a note to read it by `sections`, which returned the same first 100,000 characters again, and its outline said `convert_document` returned it whole | `test_mcp_server.py::TestConvertDocument::test_long_document_without_units_is_told_to_raise_max_chars_not_to_read_by_sections`, `TestDocumentOutline::test_document_without_units_longer_than_max_chars_is_not_said_to_be_returned_whole` |
| The MCP server keeps its last 4 results (each at most 4 million characters of text and sections, pictures dropped) keyed by the SHA-256 of the file content (hashed in a thread, off the event loop), the file name and the character limit; each call still reads the file. A result a wall-clock limit changed (`ConversionResult.time_limited`: the PDF time budget sent pages to simple extraction or left pending pages unread again) is not kept | An agent reads a long document as `document_outline` and then `convert_document` by `sections`, and every call converted the whole file again (a big PDF: tens of seconds each). Keyed by path, size and modification time, a file rewritten in place within the time resolution would be answered from the old conversion; reading and hashing costs a fraction of converting. The bounds keep the cache to tens of MB. A PDF read on a busy machine came out degraded by the time budget and was then served degraded to every later call, where before the next call converted it again; the budget warning alone misses pending pages left unread again | `test_mcp_server.py::TestRepeatedCalls`, `test_converter.py::TestTimeLimitedResults` |
| On POSIX the MCP server converts through `IsolatedConverter` (one worker per file, ended after 2 minutes and, on Linux, at 2 GB); elsewhere in a thread | The server lives as long as the agent's session, and a document that hangs or balloons must not end it. `IsolatedConverter` is verified on Linux and macOS only (limitations.md) | `TestWhichFilesMayBeRead::test_conversion_runs_in_a_worker_process`, `TestCommandLine::test_server_speaks_mcp_over_stdio` |
| Without `--root` the MCP server reads any file its user can read; with `--root` (or `OPENDOCKIT_MCP_ROOTS`) only files under those folders, checked on the path after symbolic links are resolved, and by what the folders are (device and inode), not by how their names are spelled. A root that is not a folder, or is empty, stops the server at start; `create_server` itself refuses a root that is not an existing folder (`ValueError`). The checked file is opened once, without waiting on a FIFO (`O_NONBLOCK`), and read only if what was opened is a regular file; every refusal closes the descriptor. With roots on Linux and macOS it is reached from an allowed folder one name at a time (`_opened_under_a_root`): the root is opened and compared on its descriptor (device and inode), and every name below it is opened relative to the folder before it and never through a symbolic link (`openat`, `O_NOFOLLOW`); the folders are opened for searching only where the system can (`O_SEARCH` on macOS, `O_PATH` on Linux), so a folder that may be passed through but not listed is passed through; where Python offers neither (some Python 3.12 builds for macOS lack `O_SEARCH`) such a folder still refuses the files under it. What is guaranteed there: the file read was, when it was opened, a regular file under the folder the server was given, whatever is renamed, replaced or linked between the check and the open — the file itself, a FIFO in its place, any folder above it, the root. Not guaranteed: (1) a hard link inside a root to a file outside it is that file under another name and is read — it cannot be told apart; (2) where a name cannot be opened relative to a folder (Windows; there `O_NOFOLLOW` and `O_NONBLOCK` do not exist either) the file is opened by name and then its real path is looked up again: it must name the opened file (device and inode) and lie under a root (`_still_under_a_root`), which narrows the time for a swap but does not close it; (3) without roots nothing is restricted, so only the regular-file and FIFO rules apply | The server is started by the user for their own agent, like a command-line tool, and has to work with one line of configuration. The restriction is for agents that read untrusted text and could be talked into opening something else; it is checked on the real path because a link inside an allowed folder is the obvious way around it. Compared as text, `--root ~/documents` refused files under `~/Documents` on macOS, and a Korean folder name typed composed refused the same name as a directory listing returns it. An empty `--root` (an unset shell variable) used to mean the current folder, and an empty environment variable no restriction. Given a file as a root, `create_server` allowed nothing and every call failed as 'outside the folders'. Checked by name and opened by name again, the file could be swapped in between for a link out of the folders or a FIFO that blocked the read. Opened once with `O_NOFOLLOW` and compared with the name again, only the last name was guarded: a parent folder replaced after the check by a link to a folder outside was followed by the open and by the comparison alike, and the file of the same name there was read. A folder put in place of the file was opened and never closed (one descriptor per call). Folders opened for reading refused every file under a folder that may be passed through but not listed (`chmod 711`), which its name reads | `TestWhichFilesMayBeRead`, `TestFileSwappedAfterTheCheck`, `TestCommandLine::test_empty_root_is_an_error`, `TestCommandLine::test_root_that_is_not_a_folder_is_an_error_before_the_server_starts` |
| Tool errors are the converter's fixed messages or one of the server's own fixed sentences; nothing of the document or of a parser error is in them. Text that comes from the document into an answer the server composes (titles and other metadata in the outline, names inside warnings) is put on one line of bounded length. Known accepted gap: an argument of the wrong type (`max_chars: 50.5`) is refused by the SDK's validation, in its words; `sections` is accepted as a number too, the likely slip | The rule of the whole library (core.md): messages can be shown as they are. A title holding line breaks and `Warnings:` added lines to the outline that looked like the server's own | `TestConvertDocument::test_malformed_sections_are_refused_with_one_fixed_message`, `test_file_that_cannot_be_converted_reports_the_converter_message`, `test_sections_may_be_given_as_a_number`, `TestDocumentOutline::test_title_cannot_add_lines_to_the_outline` |
| Both MCP tools carry the read-only hint and a title (on the tool and in its annotations); a file that cannot be read gives one fixed sentence, not the system's error text. `opendockit-mcp` is installed with the package whether or not the extra is: without the SDK it ends with the install command | Clients decide from the hint whether to ask the user before a call, and show the title where a tool is listed; the Anthropic Software Directory asks for `title`, `readOnlyHint` and `destructiveHint` on every tool. The command exists in every install because console scripts cannot depend on an extra, and a traceback is not an answer | `TestCommandLine::test_tools_are_described_for_the_agent`, `test_command_without_the_sdk_says_what_to_install`, `TestWhichFilesMayBeRead::test_file_without_read_permission_is_refused_with_a_fixed_message` |
| The MCP module is written against MCP SDK 2.x (`MCPServer`) and the extra requires `mcp>=2.0` | 2.0 renamed the server class and changed its module; supporting both would be two code paths for one small file | `TestCommandLine::test_tools_are_described_for_the_agent` |
| The MCP server announces tools only: the handlers the SDK registers on every server for prompts and resources are removed from its table (a private attribute; when it is not where expected the server works and announces them again) | A client builds the agent's tool list from the announcement. ## Known accepted gaps

- No adapter describes pictures; scanned PDFs come back empty with a warning unless the caller converts with a describer.
  The Open WebUI loader fails such a file with a sentence that says OCR is needed.
- The MCP server speaks stdio only. Remote transports would need authentication and a different answer to "which files".
- On Windows the MCP server has no worker isolation and no time limit of its own.
- The Dify plugin serves Workflows and Chatflows, not a Dify knowledge base: Dify 1.19 refuses `.hwp` and `.hwpx` files
  uploaded there (`source=datasets`, "File type not allowed."), whatever extensions a pipeline's upload node lists.
- The conversions of one Dify plugin process take turns, and the queue has no bound: a long queue of large files (an
  iteration run in parallel) waits its turn, and on self-hosted Dify a request its caller gave up on is still converted
  when its turn comes.
- The Open WebUI loader has no TLS of its own: across machines it belongs behind a proxy or on a private network.
