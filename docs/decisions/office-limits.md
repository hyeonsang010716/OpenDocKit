# Office processing-time decisions

Processing-time decisions of the DOCX and PPTX extractors (`docx.py`, `pptx.py`): work that was not proportional to the input size made proportional, and stopping at the character limit even inside one large table (shared with HWP/HWPX). Split off from [office.md](office.md);
the rule is the same: do not revert the decisions in this table. To change one, change its pinning test first and write the reason in the same row.

## DOCX / PPTX processing time

| Decision | Why | Pinned by |
| --- | --- | --- |
| The character look of a DOCX run (strikethrough, symbol font, ordinary font, painted-box run) is read once per run and kept (`_docx_runs._RunLook`, run_looks of `_paragraph_text`). 'Is the run text only a box' of the painted-box test (`_is_box_only`) is also computed once per run | The run properties were looked up for every w:t (scanning all children when there is no w:rPr) and the whole run text joined again, so a single run with many w:t was quadratic in their number (38 KB document 312 s → 0.05 s) | `test_office_scaling_and_note_order.py::TestDocxLongRunsAndDeepFields::test_run_with_many_text_pieces_takes_linear_time`, `test_box_run_split_into_pieces_is_still_painted_when_highlighted` |
| For DOCX complex fields, 'inside an instruction' is decided by the number of fields on the instruction side, and 'is the result text empty' by a running count of non-blank pieces per piece (`has_text_since`). Places that swap pieces (script runs, ruby) discard the counts after them (`forget_from`) | The whole field stack was scanned for every text piece and all pieces after a field were joined every time a field ended, so deeply nested fields were quadratic in depth (32,000 levels 49 s → 1.1 s) | `test_office_scaling_and_note_order.py::TestDocxLongRunsAndDeepFields::test_deeply_nested_fields_take_linear_time`, `test_field_nested_in_an_instruction_and_blank_equation_field_are_unchanged` |
| Position and bullet inheritance of PPTX placeholders is looked up with `pptx._placeholder_base` instead of python-pptx's `_base_placeholder`: per slide part a table idx → layout placeholder, and per master part type → master placeholder, built once and kept on that part. The position is `_effective_offset` (own frame → inherited placeholder; the same rule as python-pptx) | python-pptx scans the placeholders of layout and master from the start on every call, so a slide with many inheriting placeholders was quadratic in their number (1,000 placeholders 89 s → 0.5 s). Confirmed that some 490,000 shape values and the inheritance targets of 634 real decks are all the same as with python-pptx | `test_office_scaling_and_note_order.py::TestPptxManyInheritedPlaceholders` |
| The character limit (`max_chars`) is checked per cell even inside a top-level table (`_notation.TableBudget`, shared by DOCX/HWP/HWPX — for HWP/HWPX, [hwp.md](hwp.md) points to this row). When 'characters already counted + `solid_length` of the cell text read in this table' passes the limit, the remaining cells are not read, and the rendered table is counted as usual per top-level block (`Extraction.count` is not called twice). Only cell text that actually lands in the table is counted: cells at a position taken by an earlier cell or its span (the count as written in the file) (dropped in DOCX; moved to the next free position in HWP/HWPX — undercount) and the continuing cells of a DOCX vertical merge (copies of the cell above) are not counted, and with a cell whose position is unknown (HWPX without `cellAddr`) or more than 1 million remembered covered positions, the remaining cells of that table are not counted. Tables inside tables, footnotes and headers are not counted (undercount), and a DOCX header or footer table is checked against its own characters only (a budget that starts at zero): headers are read after the body but written before it, so with the body's characters charged to it a header table stopped after its first row and the text returned was not the front of the full conversion; not checked at all, a 200,000-row header table was rendered to the end again (39 s, 2.0 GB → 3 s). Once the text written before a header or footer part — the kept header text, then the body as counted, then the kept footer text — is over the limit, the remaining parts are not rendered (`docx._header_footer_text`): the output is cut inside what is already there. With each table checked alone, 40 header and 40 footer parts with a 5,000-row table each, every one under the limit, were all rendered (74 s → 2.5 s). Known accepted gap: a part whose text repeats an earlier part is dropped only after it is rendered, so copies of one large header table, which add nothing to the count, are each rendered to the end. The `text` on exceeding is the table rendered up to the rows read (header row and HTML-or-not may differ from the table rendered to the end — the document is over anyway). Known accepted gap: a table whose lower rows are dropped by the grid cell limit (5 million cells) can stop early by counting rows that would be dropped (it would take filling 5 million cells with fewer characters than the limit, which no real document does) | Counting only per top-level block meant a single table of hundreds of thousands of rows was rendered to the end before it was known to be over (200,000-row DOCX 33 s, 2.3 GB → 4.6 s, 1.5 GB; 100,000-row HWPX 7.4 s → 1.6 s. Most of the remaining time and memory is parsing the whole XML). 0 verdict violations over 230 real documents × 5 limits (N-1, N, N+1, N/2, N/3), no output change over 342 real documents | `test_office_table_char_limit.py::TestCharacterLimitInsideOneTable`, `TestLimitIsExactAroundTables` (confirmed RED when overlapping cells are counted), `TestCharacterLimitInsideOneTable::test_header_table_is_not_cut_by_the_characters_of_the_body`, `::test_header_table_longer_than_the_limit_stops_reading_rows`, `::test_header_table_of_many_rows_is_not_rendered_to_the_end` (timing), `TestHeaderPartsPastTheLimit` |
| PPTX table rows are iterated by taking `table._tbl.tr_lst` once instead of `table.rows` (`_render_pptx_table`). The authors of XLSX threaded comments (persons) are read once per workbook and passed to the sheets (`_xlsx_people`) | python-pptx's `_RowCollection` has no iterator, so the list was rebuilt per row, quadratic in the number of rows (8,000 rows 21 s). The workbook relationships file (as many entries as sheets) was parsed again per sheet, quadratic in the number of sheets (3,200 sheets 8.9 s) | `test_office_round43.py::TestPptxTableRows::test_many_rows_take_linear_time`, `TestManySheets::test_workbook_relationships_are_not_read_again_for_every_sheet` |
| A PPTX table checks the character limit per cell as well (`_notation.TableBudget`, `pptx._place_pptx_cells`), by the same counting rules as the DOCX row above (a cell at a position an earlier cell or its span already takes is dropped by `TableGrid` and not counted). It is charged with the characters of the slides before it; the shapes before it on its own slide are not counted (undercount) | Counted only per slide, a slide table of 1,000,000 rows × 1 column (587 KB) was rendered to the end before the slide was found to be over: 20 s, 3.2 GB → 1.7 s, 2.2 GB (the rest is parsing the slide XML). No output change for tables under the limit | `test_office_table_char_limit.py::TestPptxCharacterLimitInsideOneTable`, `TestLimitIsExactAroundTables::test_slide_tables_and_charts_match_the_real_length_at_every_limit` |
| The value rows of a PPTX / DOCX / XLSX / HWPX / ODT / ODP chart (`_charts.render_chart`, `render_chartex`, argument `room`; ODF writes the chart's own value table through the same `_charts._value_rows`) stop at the first row at which their cell text (`solid_length`) passes the characters the output can still take (`_notation.chars_left`: the limit minus the characters already counted; a chart in a DOCX header, footer or note, or in an HWPX note, header or footer, against its own characters only, as a table there is; an ODF chart anywhere against the characters counted so far, as every ODF flow is written after them: headers and footers are read before the body, notes and speaker notes are written after the text they are read in). The header row is not counted (undercount). Display formats (dates, percentages, units) are worked out only for the rows that are written (`_charts._Points`). Deliberate: no fixed cap on points with a warning — `max_chars` stays the only volume limit, as for table rows, and a chart within the limit renders as before. Known accepted gaps: as for tables, a column empty in the rows read is dropped although later rows fill it (the document is over anyway); every cached point is still read into memory (proportional to the XML, which is parsed anyway) | A chart had no limit of its own: the slide or block holding it was counted only after the whole value table was built, so 1,000,000 cached points (a 5 MB PPTX) took 9.0 s, 2.5 GB → 2.7 s, 1.8 GB; an ODT chart of 20,000 rows under a 5,000-character limit counted 517,000 characters (0.95 s → 0.04 s, 8,400 counted) | `test_office_table_char_limit.py::TestChartValuesPastTheLimit`, `TestLimitIsExactAroundTables::test_slide_tables_and_charts_match_the_real_length_at_every_limit`, `TestChartValuesPastTheLimit::test_odf_chart_stops_at_the_limit`, `::test_odf_cut_chart_is_the_front_of_the_full_conversion` |
