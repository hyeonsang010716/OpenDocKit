# Office processing-time decisions

Processing-time decisions of the DOCX and PPTX extractors (`docx.py`, `pptx.py`): work that was not proportional to the input size made proportional, and stopping at the character limit even inside one large table (shared with HWP/HWPX). Split off from [office.md](office.md);
the rule is the same: do not revert the decisions in this table. To change one, change its pinning test first and write the reason in the same row.

## DOCX / PPTX processing time

| Decision | Why | Pinned by |
| --- | --- | --- |
| The character look of a DOCX run (strikethrough, symbol font, ordinary font, painted-box run) is read once per run and kept (`docx._RunLook`, run_looks of `_paragraph_text`). 'Is the run text only a box' of the painted-box test (`_is_box_only`) is also computed once per run | The run properties were looked up for every w:t (scanning all children when there is no w:rPr) and the whole run text joined again, so a single run with many w:t was quadratic in their number (38 KB document 312 s → 0.05 s) | `test_office_scaling_and_note_order.py::TestDocxLongRunsAndDeepFields::test_run_with_many_text_pieces_takes_linear_time`, `test_box_run_split_into_pieces_is_still_painted_when_highlighted` |
| For DOCX complex fields, 'inside an instruction' is decided by the number of fields on the instruction side, and 'is the result text empty' by a running count of non-blank pieces per piece (`has_text_since`). Places that swap pieces (script runs, ruby) discard the counts after them (`forget_from`) | The whole field stack was scanned for every text piece and all pieces after a field were joined every time a field ended, so deeply nested fields were quadratic in depth (32,000 levels 49 s → 1.1 s) | `test_office_scaling_and_note_order.py::TestDocxLongRunsAndDeepFields::test_deeply_nested_fields_take_linear_time`, `test_field_nested_in_an_instruction_and_blank_equation_field_are_unchanged` |
| Position and bullet inheritance of PPTX placeholders is looked up with `pptx._placeholder_base` instead of python-pptx's `_base_placeholder`: per slide part a table idx → layout placeholder, and per master part type → master placeholder, built once and kept on that part. The position is `_effective_offset` (own frame → inherited placeholder; the same rule as python-pptx) | python-pptx scans the placeholders of layout and master from the start on every call, so a slide with many inheriting placeholders was quadratic in their number (1,000 placeholders 89 s → 0.5 s). Confirmed that some 490,000 shape values and the inheritance targets of 634 real decks are all the same as with python-pptx | `test_office_scaling_and_note_order.py::TestPptxManyInheritedPlaceholders` |
| The character limit (`max_chars`) is checked per cell even inside a top-level table (`_shared.TableBudget`, shared by DOCX/HWP/HWPX — for HWP/HWPX, [hwp.md](hwp.md) points to this row). When 'characters already counted + `solid_length` of the cell text read in this table' passes the limit, the remaining cells are not read, and the rendered table is counted as usual per top-level block (`Extraction.count` is not called twice). Only cell text that actually lands in the table is counted: cells at a position taken by an earlier cell or its span (the count as written in the file) (dropped in DOCX; moved to the next free position in HWP/HWPX — undercount) and the continuing cells of a DOCX vertical merge (copies of the cell above) are not counted, and with a cell whose position is unknown (HWPX without `cellAddr`) or more than 1 million remembered covered positions, the remaining cells of that table are not counted. Tables inside tables, footnotes and headers are not counted (undercount). The `text` on exceeding is the table rendered up to the rows read (header row and HTML-or-not may differ from the table rendered to the end — the document is over anyway). Known accepted gap: a table whose lower rows are dropped by the grid cell limit (5 million cells) can stop early by counting rows that would be dropped (it would take filling 5 million cells with fewer characters than the limit, which no real document does) | Counting only per top-level block meant a single table of hundreds of thousands of rows was rendered to the end before it was known to be over (200,000-row DOCX 33 s, 2.3 GB → 4.6 s, 1.5 GB; 100,000-row HWPX 7.4 s → 1.6 s. Most of the remaining time and memory is parsing the whole XML). 0 verdict violations over 230 real documents × 5 limits (N-1, N, N+1, N/2, N/3), no output change over 342 real documents | `test_office_table_char_limit.py::TestCharacterLimitInsideOneTable`, `TestLimitIsExactAroundTables` (confirmed RED when overlapping cells are counted) |
| PPTX table rows are iterated by taking `table._tbl.tr_lst` once instead of `table.rows` (`_render_pptx_table`). The authors of XLSX threaded comments (persons) are read once per workbook and passed to the sheets (`_xlsx_people`) | python-pptx's `_RowCollection` has no iterator, so the list was rebuilt per row, quadratic in the number of rows (8,000 rows 21 s). The workbook relationships file (as many entries as sheets) was parsed again per sheet, quadratic in the number of sheets (3,200 sheets 8.9 s) | `test_office_round43.py::TestPptxTableRows::test_many_rows_take_linear_time`, `TestManySheets::test_workbook_relationships_are_not_read_again_for_every_sheet` |
