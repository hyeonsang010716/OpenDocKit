# HWP / HWPX decisions

Deliberate decisions of the HWP and HWPX extractors (`hwp.py`, `hwpx.py`; the paragraph rules both follow are in `_hangul.py`). Split off from [extractors.md](extractors.md); the rule is the same:
do not revert the decisions in this table. To change one, change its pinning test first and write the reason in the same row.

## HWP / HWPX

| Decision | Why | Pinned by |
| --- | --- | --- |
| The body of an HWP distribution (read-only) document is not decrypted | That would circumvent a copy-protection mechanism | `test_hwp.py::test_distribution_document_falls_back_to_preview_with_warning` |
| An HWP document whose FileHeader attribute has bit 4 (DRM), 8 (public-certificate encryption) or 10 (public-certificate DRM) set is `EncryptedDocumentError` with one fixed message; the body is not read. A distribution document that also has one of these bits keeps the preview fallback of the row above | Its body streams are encrypted: read as usual they gave an empty result or 'corrupted'. The bit meanings are those of the 5.0 spec, as in pyhwp (`drm`, `cert_encrypted`, `cert_drm`) and hwp.js. **Not verified with a real DRM or certificate-encrypted file** | `test_hwp.py::TestProtectedDocuments` |
| When the compression of the HWP DocInfo stream is broken (zlib.error), the body is read without it (no styles, numbering, character shapes or pictures) with one warning | DocInfo holds no text; one broken DocInfo rejected documents whose sections were fine (the same rule as a broken HWPX header.xml) | `test_hwp_robustness.py::TestBrokenDocInfo` |
| The HWP cell address is read 8 bytes after LIST_HEADER (6 is tried too) | The spec document (6) and real files (8) differ | `test_hwp.py::test_converts_heading_footnote_and_merged_table` |
| The BinItem ID of an HWP picture is read 71 bytes after SHAPE_COMPONENT_PICTURE | The sum of the spec's structures, confirmed on 3 kinds of real file | `test_image.py::test_hwp_picture_via_bin_data` |
| `max_uncompressed_bytes` applies to HWP stream decompression (total per document) | It is raw deflate, so the size is unknown before decompressing: 284 KB decompressed to 300 MB | `test_hwp.py::test_compressed_stream_is_bounded_by_uncompressed_limit` |
| The number of HWP records is limited per document to `max_uncompressed_bytes // 128` (about 4.1 million by default); beyond that it is a `DocumentTooLargeError`. The body is streamed one top-level record at a time with `iter_records` (nothing is counted after stopping at the limit), and DocInfo is parsed only once. Known accepted gap: with `max_chars=None` a real document of around 140 MB of decompressed body is rejected too | 16 million zero-size records (62 KB compressed) took 12 s and 2.4 GB (→ rejected in 2.3 s). Real files average 35 bytes per record (26 even for an empty paragraph), so the default character limit stops much earlier. The remaining worst case (4 million records under one paragraph) is 2.4 s and 0.7 GB, on a par with 4 million empty HWPX paragraphs | `test_hwp.py::TestHwpRecordBudget` |
| HWP paragraph text (PARA_TEXT) is decoded in one go from the byte ranges between control characters (`00~1f 00` starting at an even byte) (`hwp.decode_para_text`), and the character-shape runs (PARA_CHAR_SHAPE) are read as an array keeping only the places where the marking changes (`_shape_runs`; anything past the text length is dropped). The result is the same as the earlier per-character decoding (compared on 8,777 paragraphs of 26 real HWP files and 20,000 random ones) | Making a Python integer per character (tuples, lists) used 1.9 GB for a single paragraph of 24 million characters before the character limit was looked at (→ 0.47 GB). The limit is still checked per paragraph — a single paragraph is decoded to the end | `test_hwp_robustness.py::TestHugeParagraphText` |
| Integer attributes are read with `_package.decimal_int` (HWPX `_int`, autoNum; '²' and numbers over 4,300 digits give the default). HWP section stream names use `isdecimal()`. When content.hpf is broken, the body goes by section number order, pictures by BinData file name (= manifest id), without metadata. Parts outside the body (header.xml, content.hpf, manifest, preview) do not stop the body from being read on XML, CRC or compression errors — without styles when header.xml cannot be read (warning), without knowing whether it is encrypted when the manifest cannot be read (an encrypted body is corrupted anyway) | A single '²' or one broken content.hpf rejected the whole document (the docstring said it falls back to number order). So did one XML error in header.xml, one CRC error in a part, or one 5,000-digit rowAddr | `test_hwp.py::TestOneOddValueInHangulDocuments`, `test_hwp_robustness.py::TestHwpxPartsOutsideTheBody`, `TestHugeNumbersInHangulDocuments` |
| An HWP picture stream is read only once per BinItem, and a picture with broken compression is skipped on its own | Decompressing again per reference took 150 s and 1.4 GB for a document with 16,384 references to a picture, and the decompression limit was also consumed per reference | `test_image.py::TestHwpRepeatedAndBrokenPictures` |
| HWP summary information is read directly, title and author strings only, instead of olefile's `getproperties` | It trusted the vector count and looped 4.3 billion times on an 8-byte manipulation, and in 21 of 22 healthy files binary data came out after the title | `test_hwp.py::TestHwpSummaryInformation` |
| An HWPX picture file is decompressed only once, and a broken picture is skipped on its own | 80 references to a 40 MB picture took 3.4 GB | `test_image.py::TestResourceBounds::test_hwpx_picture_referenced_many_times_is_read_once` and 1 more |
| An HWPX member that cannot be read is broken whatever the reason: besides bad compression and CRC, an unknown compression method (NotImplementedError), the ZIP encryption flag (RuntimeError) and other errors of reading one member (`hwpx._MEMBER_ERRORS`, the tuple ODF uses). A section, picture, chart or part outside the body that cannot be read is handled like a broken one | Only bad compression and CRC were caught, so one such picture, header.xml or section rejected the whole document | `test_hwp_robustness.py::TestHwpxUnreadableMembers` |
| Hangul (HWP) paragraph numbers and bullets are built from the head of the paragraph shape (HWP PARA_SHAPE→NUMBERING/BULLET, outlines at byte 18 of the section definition / HWPX hh:heading). A bullet is '- ' whatever its glyph; without a number when the definition is broken. 'Start new numbering' is not reflected. Lower-level numbers in the body take the same `list_item_prefix` form as DOCX/PPTX (`  - 가. `, `    - 1) `; `_lists.paragraph_head`), the top level stays as is, and an outline paragraph that becomes a heading gets the number only (no bullet) | The number is not text but paragraph shape, so '1.' and '가.' were missing. Lower levels only got indentation, which `clean_text` removed, and a blank line appeared per item, so '1) 매출 감소' under '가. 현황 분석' read at the same level | `test_hwp.py::TestParagraphNumbering`, `TestHwpxObjects::test_paragraph_numbers_and_bullets_are_kept`, `test_hwp_heads_and_shapes.py::TestLowerLevelNumbers` |
| The level of a bullet paragraph is set from the left margin (first INT32 of HWP PARA_SHAPE, HWPX hh:margin/hc:left — the first one in an hp:switch) (`_lists.BulletNesting`): one level down only when it has the same level as the unclosed bullet item right before it and a larger margin (by more than 100); with the same or a smaller margin that item is closed. A non-bullet paragraph (number, heading, body) closes only items indented further, and all of them when its margin is 0. The top-level body and inner paragraph lists (cell, footnote, text box, caption) are counted separately. A bullet whose level differs from a numbered paragraph stays as it is. Known accepted gap: hanging indents are not looked at, and a paragraph holding only a table does not close items | A Hangul report that made □, ○ and - as different bullet definitions, all at level 0, and expressed the hierarchy through margins alone became a flat `- ` list. It only compares with the previous item, so the output of a list whose margins are all equal does not change (same direction as DOCX `_list_depth`). **Verified with synthetic documents only, no real Hangul file** | `test_hwp_heads_and_shapes.py::TestBulletNestingByMargin` |
| An HWPX check bullet (hh:bullet has checkedChar) puts checkedChar after `- ` when the paragraph shape is checked (hh:paraPr checked="1"), otherwise char (`- ☑ 안전모 착용 확인`, `- ☐ …`; `hwpx._check_mark`). When the character is in the private-use area (it is removed anyway), just `- ` as before. Known accepted gap: for the HWP binary format it could not be confirmed from the public spec or hwplib which value of the paragraph shape or bullet record holds the checked state, so only `- ` is produced (not read from a guessed bit — if wrong, done and not done would be swapped) | Everything came out as just `- ` and done/not done of a checklist was lost. **Verified with synthetic documents only, no real Hangul file** | `test_hwp_heads_and_shapes.py::TestHwpxCheckBullets` |
| A top-level table checks the character limit while reading cells (`_notation.TableBudget`; the decision and accepted gaps are in the same row of [office-limits.md](office-limits.md)). A cell whose address overlaps (one that is moved to the next free position) is not counted (undercount) | A 100,000-row HWPX took 7.4 s and 2.3 GB, and HWP too only learned it was over after rendering a table to the end | `test_office_table_char_limit.py` |
| When a cell address (HWPX `hp:cellAddr`, HWP LIST_HEADER) points at a position already taken by an earlier cell or its span (two cells with the same address, a span larger than the table), a cell with text is put at the next free position of that row (`markdown.TableGrid.place_or_next` → the same `place_next` as for cells without an address). An empty cell is dropped as before | In corrupted files the text of later cells disappeared without a warning ('가2', '가3' lost). DOCX computes cell positions by order so they never overlap, and keeps `place` | `test_hwp_robustness.py::TestCellsOnAnOccupiedAddress`, `test_office_table_char_limit.py::TestLimitIsExactAroundTables` |
| The paragraph head (number, bullet) and the outline heading mark are attached only to the first text piece of the paragraph (text continuing after a table, text box or chart gets neither head nor `#`). A piece holding only placeholders (picture, OLE object, video) is not text (`_lists.is_placeholder_only`). When the paragraph ends up with no text, only the number is attached to that piece; a paragraph without even such a piece, holding only tables, text boxes or charts, gets the number alone as a block in front of them (`2.`) (the count is kept; no heading mark or bullet. Known accepted gap: a lone `2.` is not a list line and is separated from the previous item by a blank line) | In a numbered paragraph where a picture precedes the table or text box, the number went to the picture piece, '2.' was left alone and '추진 목표' lost its number. Of an outline paragraph only `#` was left alone, and even the piece after the split by a table became the heading '# 은 아래와 같다'. A numbered paragraph holding only a table or text box was not counted, so '3. 추진 일정' on the Hangul screen moved up to '2.' | `test_hwp_heads_and_shapes.py::TestHeadOfAParagraphThatStartsWithAPicture`, `TestOutlineParagraphSplitByATable`, `test_hwp_object_only_numbers.py` |
| An HWPX shape filled with a picture (hc:fillBrush/hc:imgBrush/hc:img) is registered as a picture and placed before the shape text (like PPTX picture fills). Tiled fills (mode `TILE…`) are patterns and not registered. Known accepted gap: picture fills in the HWP binary are not read (no sample, position of the fill information unconfirmed) | Not being a picture object, it dropped out without a trace | `test_hwp_heads_and_shapes.py::TestShapeFilledWithAPicture` |
| Hancom equation script (HWP equation record, HWPX hp:script) becomes ` $LaTeX$ ` through `_equation.render_equation` (the same shape as Word equations). The rules follow Hancom's public document "한글 문서 파일 구조 - 수식" (Hangul document file structure — equations) rev 1.3: terms are separated by spaces (`over` and scripts work per term, but a script that starts with `{…}` runs to the closing brace — `x^{2}+y`), a command argument is a single piece (`sqrt{x}^2` is (√x)²), BINOM takes the two following terms, `~` and `` ` `` are blank terms that take scripts, commands are case-insensitive (only Greek letters, arrows and deg are case-sensitive), and functions are recognized even when written without a space. `cdot`, `+-`, `-+`, `<=`, `>=` become `\cdot`, `\pm`, `\mp`, `\leq`, `\geq`. Unknown commands (LADDER, SLADDER, LONGDIV), unbalanced brackets, over 10,000 characters, nesting over 64 and converter exceptions give the original ` [Equation: …] ` | The raw script is hard for an LLM to read. One equation must not fail the whole document, so every failure falls back to the original. **Verified only with the spec's examples and command table and one equation from a real business document** (no other real sample) | `test_equation.py`, `test_hwp.py::TestEquations` |
| An HWP table caption is the sibling PARA_HEADER before TABLE; HWPX captions of pictures, equations, OLE, charts and text art are hp:caption (before for TOP/LEFT, otherwise after). An HWP equation (eqed) caption is the sibling paragraph below the control, put as text beside the equation; the direction is bits 0–1 of the attribute 8 bytes after the caption's LIST_HEADER (0 left and 2 top mean before) | Captions were always dropped. The equation caption ('수식 1 A') was missing for the public hwplib '수식.hwp' (position confirmed as below = 3) | `test_hwp.py::TestHwpObjects::test_table_caption_is_kept_before_the_table`, `TestHwpxObjects::test_picture_and_equation_captions_are_kept`, `TestHwpxObjects::test_text_art_caption_is_kept`, `TestEquations::test_hwp_equation_caption_is_kept_on_its_side` |
| The search for pictures in an HWP drawing object does not descend into the paragraphs inside a text box (PARA_HEADER) | The picture was registered twice and placed at the position of the outer paragraph | `test_hwp.py::TestHwpObjects::test_picture_inside_text_box_is_registered_once_where_it_is` |
| HWPX hp:switch takes hp:case first, and hp:default when no text comes out (an empty block such as an empty table is not text); a case passed over takes back the notes and comments it registered. Text art is the `text` attribute. HWP text art is the string (WORD length + UTF-16; hwplib ForControlTextArt) after the vertex coordinates (INT32×8) of SHAPE_COMPONENT_TEXTART (HWPTAG_BEGIN+74) under a drawing object (gso). Both are separate blocks; line breaks are CR, LF and ␍␊. A broken record whose length runs past the record skips only that text art | The chart is inside case and default is a fallback OLE. A case with only an empty table hid the fallback text, and a case with only a comment let the fallback register it again. Text-art text was dropped whole (both HWPX and HWP). **The HWP text-art record layout is based on hwplib and verified with synthetic records only** | `test_hwp.py::TestHwpxObjects::test_chart_data_is_kept`, `test_switch_branch_without_text_leaves_nothing_behind`, `test_text_art_is_kept`, `test_hwp_heads_and_shapes.py::TestHwpTextArt` |
| Ruby text is put in place in the paragraph text as `base(ruby)` (the two length+text pairs of the HWP `tdut` control; mainText/subText of HWPX hp:dutmal). The shape is in one place, `_notation.format_dutmal` | The base text is inside the control too, so a word with ruby text was dropped whole | `test_hwp.py::TestDutmal` |
| Composed (overlaid) characters are put in place one after another (length+text of the HWP `tcps` control, composeText of HWPX hp:compose). The overlay shape (circle, square) is discarded | The characters are inside the control or attribute, so the number in '제⑫조' was missing. Confirmed with public hwplib/hwpxlib samples (files made by Hangul) | `test_hwp.py::TestComposedCharacters` |
| HWPX form objects: check boxes and radio buttons are `☒`/`☐` + label (caption; ☒ only when value is CHECKED), list boxes give selectedValue, edit boxes hp:text. Command buttons (hp:btn) and empty values are left out. HWP form objects (`form`) are not read (no sample) | The values are in attributes and were dropped whole. The same characters as DOCX form fields and HTML forms. Structure confirmed with public hwpxlib samples | `test_hwp.py::TestHwpxFormObjects` |
| HWPX change tracking: text between hp:deleteBegin and the hp:deleteEnd with the same Id inside the same hp:t is left out (inserted text stays). Known accepted gap: when the pair is in a different hp:t, run or paragraph, the extent cannot be known for sure and the deleted text stays | The deleted value and the inserted value both read as valid values (same direction as leaving out DOCX w:del). Only properly paired ranges are removed, so documents without change tracking lose no text. The structure is from the public hwpxlib sample 'ChangeTrack.hwpx'. Pairing uses the position of the last deleteEnd per Id (linear) — scanning all following siblings took 12 s for 16,000 | `test_hwp.py::TestHwpxTrackChanges`, `TestLinearTimeOnCraftedInput` |
| A table inside a footnote or endnote (and tables inside it) is one line (`_notation.note_table`: cells ` / `, rows `; `, same as DOCX). The same for a footnote in the body and one inside a cell. A table inside a header/footer is unchanged (a Markdown table at a body position, 'cell / cell' inside a cell) | The Markdown table was rendered and then the footnote merged into one line, giving `\| 연도 \| 값 \| \| --- \| …`; a footnote inside a cell became '연도 / 값 2022 / 5' with the row boundaries lost | `test_hwp.py::TestTableInsideFootnote` |
| Caption auto numbers (HWP `atno`, HWPX hp:autoNum) are put in place only for pictures, tables and equations (including number format and surrounding decoration). Page numbers and footnote/endnote numbers are not inserted | The number is a control, not text, so '표 1' (Table 1) came out as '표'. Footnote numbers would duplicate `[^n]` | `test_hwp.py::TestAutoNumber` |
| Lower levels of a list inside a table cell are marked with `└ `, `└─ ` (`_lists.cell_level_mark`). Known accepted gap: when a single-column table is unfolded into paragraphs the marks stay in the body | Leading spaces inside a cell are removed by `_clean_cell`, so the level was lost. `-- ` cannot be used for numbered lists | `test_hwp.py::TestListLevelsInsideTableCells` |
| When the preview consists only of cell marks (`<>`), it is not used in place of the body (empty result; for an HWP distribution document, the cannot-be-read error) | A document without text produced `<>` and the 'could not parse the body' warning | `test_hwp.py::TestPreviewFallback` |
| An HWPX comment (the subList of hp:fieldBegin type="MEMO"; the author is stringParam Author) goes not in place in the body but at the end of the document as `> Comment(author, on "range"): text` (`_notation.comment_line`, same as DOCX/PPTX). The range is the text up to the fieldEnd with the same id (joined with spaces over several paragraphs, 40 characters). A comment that has gathered enough to show gathers no more, and the space between paragraphs does not scan comments whose range ends empty or in whitespace (`_unspaced_memos`) — a comment without fieldEnd took time quadratic in the number of paragraphs, and 24,000 comments attached to empty paragraphs took 16 s. The commented body text stays as it is. Known accepted gap: HWP binary comments (`%%me`) are still not read, as there is no evidence from spec or samples for which record holds the comment text (two real files only confirmed that the commented body text is kept), and the reply structure of HWPX comments is not handled | Comments dropped out without a warning and the LLM could not see review remarks. The earlier reason ("same direction as DOCX comments") reversed once DOCX started including comments (round 38) | `test_hwp.py::TestMemo` |
| Hangul strikethrough is `~~text~~` (`_inline.mark_strike`, `resolve_strikes`). HWPX only when `hh:strikeout shape` is an OWPML LineType2 line kind (`NONE` and the out-of-spec `3D` excluded); HWP only when the value of character-shape attribute bits 18–20 is 1 and the shape in bits 26–29 is 0–10 (solid to thin+thick+thin). Wave (11, 12) and 3D (13–15) are not strikethrough in either format — hwp2hwpx maps only 0–10 to line kinds on HWP → HWPX and the rest to NONE | Deleted values stayed as plain text and '월 100,000원 80,000원' read as two values. Conversely, looking at bits 18–20 alone wrapped the entire body and tables of 15 real government press-release HWP files in `~~`: that character shape is bit 18 + shape 15, and the HWPX of the same documents (character-shape indexes 1:1, 342 in 16 pairs) had `3D`. Shape 7 pairs with HWPX `DOUBLE_SLIM`. After the fix the output of 17 of 18 HWP/HWPX pairs is the same. **There is still no sample in which text is actually struck through** | `test_hwp.py::TestStrikethrough` |
| HWP/HWPX also resolve strikethrough before scripts (`resolve_scripts(resolve_strikes(…))`, the same order as DOCX/PPTX; see the explanation of `_inline.resolve_strikes`) | Resolved the other way round, a struck superscript '-', '3' split over two runs (in HWP, pieces split by the extended control between them) broke into `~~10^-^3~~`. 0 output changes over 25 real HWP and 6 HWPX files (no sample of a struck script) | `test_hwp.py::TestStrikethrough::test_hwpx_struck_superscript_split_over_runs_is_one_superscript_inside_the_strike`, `test_hwp_struck_superscript_split_over_runs_is_one_superscript_inside_the_strike` |
| The content of Hangul OLE objects (HWPX hp:ole, SHAPE_COMPONENT_OLE of an HWP gso) and videos (HWPX hp:video) is not read: `[OLE object]`/`[Video]` placeholders + a count warning. The preview (OlePres000) is not registered, and the placeholder stays even when picture extraction is off (DOCX/PPTX use the same placeholder and warning only when the preview picture cannot be registered — OLE row of [office.md](office.md)). HWP video records are not handled for lack of a sample | Pasted sheets and charts disappeared without a trace. The preview is a proprietary header + WMF and cannot be decoded | `test_hwp.py::TestEmbeddedObjects` |
| The HWP record tree is descended with a stack (`_flatten`, `HwpRenderer.render`; no recursion). The depth of entering paragraphs inside controls (table cells, text boxes, footnotes) goes up to `_MAX_NESTING` (128); anything deeper is not read, with a warning. Known accepted gap: the inside of tables 129–200 levels deep, which used to be read, is dropped | A chain of 1,000 unknown records (body, DocInfo, drawing objects) and 400 levels of table inside table rejected the whole document with a RecursionError. The outer levels and the paragraphs before and after are kept. A 128-level table uses about 400 of the default recursion limit of 1,000, leaving room for the caller's stack | `test_hwp_robustness.py::TestDeepRecordChains` |
| When the compression of one HWP section stream is broken (zlib.error), only that section is skipped; when it is truncated without an end marker (`decompressobj.eof` false), what was read is used. Both give a `Section N:` warning. When every section is broken it is a corrupted document as before. Known accepted gap: truncation of an uncompressed stream cannot be detected | One broken Section1 rejected a whole document whose Section0 was fine, and a truncated stream gave only its front part without a warning. **Whether section streams of real HWP files always have an end marker was verified with synthetic files only** (Hangul writes complete deflate) | `test_hwp_robustness.py::TestBrokenSectionStream` |
| An XML error or compression (CRC) error in one HWPX section (section*.xml) skips only that section with the warning `Section N: corrupted and could not be read.` (N is the body order). When every section is broken it is a corrupted document as before | One broken section rejected a whole document whose other sections were fine (same direction as the section isolation of HWP) | `test_hwp_robustness.py::TestBrokenHwpxSection` |
| An HWPX chart part (`hp:chart chartIDRef`) is read, parsed and rendered once however many `hp:chart` point at it; its values are written at the first reference and later ones give the `[Chart] title` line. A part that cannot be read is tried once | 50 references in one paragraph to a part of 300,000 empty elements (7.8 KB) took 22 s, 100 took 47 s; the output is about 9 characters per reference, so `max_chars` never stopped it. Same rule as the ODF embedded object | `test_audit_hangul.py::TestHwpxChartReferencedManyTimes` |
| A section listed again in the `content.hpf` spine is read once, and at most 5,000 itemrefs are looked at (the rest are reported in a warning) | One section of 300,000 empty paragraphs listed 40 times (33 KB) was parsed and rendered 40 times, 29 s. Same two guards as the EPUB spine | `test_audit_hangul.py::TestHwpxSpine` |
| The prefix / suffix character of an HWP auto number (`atno`) in 0xD800–0xDFFF is dropped | The raw UINT16 went through `chr()`, and a lone surrogate made the result impossible to encode as UTF-8 (same as RTF `\uN`) | `test_audit_hangul.py::TestHwpAutoNumberDecoration` |
| An HWPX section file number that `int()` cannot read (over 4,300 digits) sorts after the numbered sections in the fallback order | `int()` ran before the spine was looked at, so one extra member with such a name rejected the whole document | `test_audit_hangul.py::TestHugeHwpxSectionNumber` |
| A Hancom equation whose term carries two superscripts or two subscripts (`x^2^3`) keeps the original ` [Equation: …] `. Known accepted gap: it is neither nested nor grouped, as the specification does not say what Hancom draws | It came out as `x^{2}^{3}`, which LaTeX rejects (double superscript) | `test_audit_hangul.py::TestEquationWithARepeatedScript` |
| The N of an HWP `Section N:` warning is the position in the body (as for HWPX), not the number in the stream name | Up to 24 digits chosen by the document reached a warning | `test_audit_hangul.py::TestHwpSectionWarningNumber` |
| Header and footer texts already seen are looked up in a dict (order of first appearance kept), in HWP and HWPX | A list scan per header: 60,000 different headers took 11 s | `test_audit_hangul.py::TestManyDistinctHeaders` |
| A footnote or endnote takes its number once its text is rendered (HWP and HWPX, also one inside an HWPX comment). A note without text leaves neither `[^n]` nor a definition and uses up no number; a note inside a note is left out with its text, as in RTF and ODF | The number was taken before the text was rendered and read again afterwards, so a note inside a note gave both the inner number (`Body[^2] … [^2]: inner / [^2]: outer[^2]`), and an empty note left a bare `[^1]:` | `test_hwp.py::TestNotesInsideNotes` |
| Paragraph numbers in a header, footer, note or (HWPX) comment are counted with their own counters, fresh for each of them | A numbered paragraph there advanced the body's counters, so the body skipped a number after a page header | `test_hwp.py::TestNumberingOutsideTheBody` |
| A broken HWP DocInfo STYLE or BIN_DATA record (shorter than 2 bytes) keeps its place: an empty style name, a BinItem without a stream (as PARA_SHAPE already did) | IDs are positions in DocInfo; skipping the record shifted every later style name and picture stream by one | `test_hwp_robustness.py::TestBrokenDocInfoRecordsKeepTheirPlace` |
