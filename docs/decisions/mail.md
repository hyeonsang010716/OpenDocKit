# Mail decisions

Deliberate decisions of mail extraction (.eml, .mht mail, mbox) (the mail unpacking in `_mail.py` and `_mail_calendar.py`, `html._extract_mail`). Split off from [extractors.md](extractors.md);
the rule is the same: do not revert the decisions in this table. To change one, change its pinning test first and write the reason in the same row. Mail/MHTML detection and
the headers are in the MHTML and reinforced-mail-detection rows of [detect.md](detect.md).

| Decision | Why | Pinned by |
| --- | --- | --- |
| The MHTML header block is walked line by line by `_mime_header_block`. No regular expression matching the whole block and no nested quantifiers of the form `(?:…+…)*` are used. The block is looked for within the first 256 KB (`_mail.MIME_HEAD_BYTES`), and a leading mbox separator line (`From sender …hh:mm…`) is skipped only when a header block follows it (`_mail.mime_start`, common to mail and MHTML). A file that starts that way is split into mails at each such separator line at the start of a line and read as `## Message N` + headers + body (`_mail.mail_box`; up to 100 mails + a warning; HTML if any mail has an HTML body) | It backtracked as many ways as two quantifiers can share the leading whitespace of folded lines, so text whose first line is `word:` followed only by indented lines (XMP metadata, list notes) did not finish even with 12 lines (a text file named .pdf 180 s+ → 0.07 s). With an 8 KB range, Office 365 mail with long headers and .eml starting with a `From - date` line were text with the base64 as is. Of a multi-mail mbox only the first mail was read | `test_detect.py::TestMhtml::test_prose_with_many_indented_lines_is_decided_in_linear_time`, `test_folded_header_lines_and_crlf_still_make_an_mhtml`, `test_blocks_that_are_not_header_blocks_are_not_mhtml`, `test_core_mail_and_detect.py::TestMailWithALongHeaderBlock`, `TestMailWithAnMboxFromLine`, `test_core_mail_parts_and_icons.py::TestMailboxWithSeveralMails` |
| A mail 'forwarded as attachment' (message/rfc822) is read after the outer body as `## Forwarded message` + its headers + body (`_mail.mail_messages`; depth first, up to 20 — beyond that it is named in the attachment warning). The search for body parts (`_mail_parts`) does not descend into forwarded mails. Even when the outside is plain text, if a forwarded mail has only an HTML body or there is an HTML body outside alternative (HTML body or footer of a mixed; `_mail.mail_html_outside_alternative`), the HTML extractor is used (`html._extract_mail`) — reading only plain text made that HTML body disappear without a warning (`TestForwardedMail::test_forwarded_mixed_mail_keeps_both_its_plain_and_html_bodies`, `test_forwarded_alternative_with_an_html_footer_keeps_the_footer`). Mail is not passed to HTML detection (tag sniffing). All HTML body parts are joined in order (for alternative, the last branch that has HTML; `_mail.mail_html_body_parts`). A leaf part that is not the top level, has a name and has no Content-ID/Content-Location is an attachment even without a Disposition or with inline, when it is not text (text/*) (`_is_attachment`). The charset of RFC 2047 words (headers, attachment names) uses the superset codec (EUC-KR → CP949, `_mail._header_codec`). Raw 8bit headers (UTF-8, CP949) go through `decode_text` on the original bytes, mixed words separately, a run of adjacent words together so that a character split over two words is joined (`_mail._decoded_header`; `test_core_mailboxes_and_charsets.py::TestEightBitHeaderWithSplitEncodedWords`). Known accepted gap: a text part with `inline; filename=` is body | The body search descended into the forwarded mail and its HTML body pushed out the outer plain body. From the forwarder's text alone an LLM does not know the context. Plain mail with an 8bit `<html>` part was read as HTML in raw form. A text/html attachment that merely had a name pushed out the plain body. The trailing HTML of Apple Mail's `mixed > (HTML, inline PDF, HTML)` disappeared without a warning. Extended Hangul (됬, 똠) in `ks_c_5601-1987` words and Gmail attachment names came out as raw encoded words, and raw 8bit headers as `������` | `test_core_text_and_mail.py::TestForwardedMail`, `TestNamedMailPartWithoutDisposition`, `TestRawEightBitMailHeaders`, `test_core_mail_parts_and_icons.py::TestHtmlBodySplitAroundAnInlineAttachment`, `TestKoreanEncodedWordsWithExtendedHangul`, `TestEncodedAttachmentName` |
| A meeting invitation in the mail body (a text/calendar part that is not an attachment) is put after the body as `Event:` (`Event (cancelled):` for METHOD:CANCEL) + a list of `- Title/Start/End/Location/Organizer/Attendees: value` (`_mail_calendar.mail_calendar_events`; `html._calendar_html` for HTML mail; forwarded mails too). Folded lines are unfolded in the bytes before decoding (folding is per 75 octets and splits even in the middle of a Hangul character) and escapes (`\,`, `\;`, `\n`) are resolved. Times keep their time zone as written, `2024-03-07 15:00 (Korea Standard Time)`, `… UTC`, all-day `2024-03-07`; people are `name <address>`. For an all-day event whose start and end are both dates, the end is the day before (a date DTEND does not include that day — RFC 5545), and for a one-day event `End` is left out (`_mail_calendar._end_of_all_day_event`). A recurrence rule (RRULE) goes after `End` like `- Repeats: weekly on Tuesday, 4 times` (`_mail_calendar._recurrence` — only FREQ DAILY–YEARLY, INTERVAL, COUNT, UNTIL, BYDAY (including ordinals), BYMONTHDAY, WKST; any other item or frequency gives the raw rule). Up to 20 VEVENTs, 30 attendees and 1 MB per part; silently nothing when there is no readable event or it cannot be parsed. The description (DESCRIPTION) is the same as the body and is not read. A named .ics attachment gives only the attachment warning as before | An Outlook meeting invitation does not write date, time and place into the body (text/plain, text/html), so the event disappeared without a warning. Converting the time zone to UTC would need VTIMEZONE interpretation and could be wrong, so it stays as written. An all-day event on March 5 came out as 'End: 2024-03-06', and the weekly recurrence disappeared so it read as a one-off event. Unfolding after decoding garbled the Hangul at the fold into '예��' | `test_core_mail_parts_and_icons.py::TestMeetingInvitation`, `test_core_mail_bodies_and_events.py::TestAllDayAndRecurringEvents`, `test_core_html_mail_hidden_and_frames.py::TestCalendarLinesFoldedInsideACharacter` |
| A forwarded mail (message/rfc822, Exchange) wrapped in a transfer encoding (base64, quoted-printable) is decoded, read again and replaced by the mail with its parts unpacked (`_mail._forwarded_message`). When it cannot be decoded it stays as before | The parser read the wrapped text as a mail without headers, and base64 came out as is in the place of '## Forwarded message' | `test_core_mailboxes_and_charsets.py::TestForwardedMailInATransferEncoding` |
| The attachment warning (`_mail.mail_attachment_warning`) does not count detached signature parts (application/pkcs7-signature, x-pkcs7-signature, pgp-signature; `smime.p7s`), and reports Outlook's TNEF part (application/ms-tnef, vnd.ms-tnef; `winmail.dat`) separately with a sentence saying it cannot be read and that attachments and the formatted body inside it may be missing (appended to the same warning string). Up to 10 names are written, then 'and N more' (`_mail._ATTACHMENT_NAMES_SHOWN`, the same number as the PDF attachment warning); unnamed attachments and forwarded mails without a subject are given as a count only, 'N unnamed attachment(s)' (`_mail._attachment_list`). Known accepted gap: an smime.p7m that wraps the body inside the signature or encryption is still reported as an attachment — the body is inside it | A signature is not content, yet the warning asked to convert the attachment separately, and winmail.dat cannot be converted separately with this converter either, so the same advice was wrong. The single warning line of a mail with 20,000 attachments was 229 KB. Unnamed attachments were repeated 10 times as 'unnamed' | `test_core_mail_parts_and_icons.py::TestSignaturesAndTnefAttachments`, `test_core_header_tables_cell_code_and_terminal_codes.py::TestManyMailAttachmentNames`, `test_core_round44.py::TestUnnamedMailAttachments` |
| When the HTML body part has no visible text at all (no character other than whitespace and zero-width characters (ZWSP, ZWNJ, ZWJ, BOM, U+034F, soft hyphen) outside unrendered elements (`_DROP_TAGS`) and hidden elements (`_drop_hidden`); alt text is not counted — `_html_mail._has_text`), the plain-text branch is put after the HTML as paragraphs (`html._mail_body_html`; pictures stay, plain parts already read in order are left out). Deliberate: folded answers (`_folded_answers`) are not looked at. The plain text is not put in front — the `<head>` of the HTML document that follows went into the body and `<title>` came out as text | When the HTML branch of an alternative was just a logo picture (`<img src="cid:logo">`), the body in the plain branch disappeared without a warning and only the headers remained. Taking the `display:none` preview text (preheader) and `&zwnj;&nbsp;` padding of promotional mail for text caused the same | `test_core_mail_bodies_and_events.py::TestHtmlAlternativeWithoutText`, `test_core_html_mail_hidden_and_frames.py::TestHtmlAlternativeWithOnlyHiddenText` |
| The body of a mail read as HTML follows the order of `_mail.mail_body_sequence`: only multipart/alternative picks one (the HTML of the last branch that has HTML, otherwise the last branch that has a body); plain and HTML parts of mixed/related are all taken in order. Every body part, every `## Message N` / `## Forwarded message` header block and every meeting invitation is decoded and rendered as an HTML document of its own and the Markdown is joined (`html._extract_documents`; pictures numbered on, each warning once, omitted table rows added up; the documents after the one that takes the text over the character limit are not read, and each document's front-part check (`_extract_front`) gets what is left of the limit) — what one part leaves open ends with it, as a mail program shows each mail apart. The cost is one parse per part (linear: about 1 ms a part) | In a multipart/mixed with a plain body + an HTML part (signature, mailing-list footer) only the HTML was read, and the plain body with the approval details and amount disappeared without a warning. Joined into one HTML and parsed once, an unclosed `<!--`, `<style>`, `<script>`, `<title>`, attribute quote or `display:none` element in one mail swallowed every later mail of the mailbox and every forwarded mail without a warning, and an unclosed blockquote, pre or `<del>` took them into the quote, the code block or the strikethrough | `test_core_html_mail_hidden_and_frames.py::TestPlainAndHtmlBodiesSideBySide`, `test_core_mail_parts_and_icons.py::TestMailsAreRenderedApart` |
| When the charset of an RFC 2047 word is Windows-1252 or ISO-8859-1, the word's bytes are decoded by the same rule as a body declaration (`decode_text` — Windows-1252 after strict UTF-8 and CP949 decoding) (`_mail._latin_labeled_text`). But when more than half of the non-ASCII characters of the text read as CP949 are not everyday Hangul (precomposed KS X 1001), it is read as declared. Other charsets use the superset codec as before | Old mail programs wrote CP949 subjects as `=?iso-8859-1?B?…?=`, so the subject was `[°øÁö] 10¿ù …` (the body was already read as CP949). In short headers two adjacent Western European letters (ção, öß) decoded as a CP949 Han character and `Informações` became `Informa寤es` | `test_core_html_mail_hidden_and_frames.py::TestEncodedWordLabeledLatinButKorean`, `test_core_malformed_mail_and_html.py::TestLatinSubjectWithAccentedLetterPairs` |
| Mail bytes are read only through `_mail.parse_mail`: when multipart boundaries nest deeper than 32 levels (`_MAX_MIME_NESTING`) the mail is rejected as a corrupted document before parsing (`_mime_nesting_exceeds` — one pass that follows the structure the parser follows: the header block of each part, its type and boundary resolved by the standard library from the first Content-Type header (`_part_structure`), then, skipping the body, the next delimiter or closing line of an open multipart, which ends every part inside it; no recursion; the body of a delivery report (message/delivery-status), whose header blocks the parser reads as parts, is not walked that way — every `multipart/` in it counts as a level open to the end of the report, because multiparts opened one inside the other in one block went around the limit: 900 levels and 200,000 lines, 1 MB, took 43 s, each line read once), and after reading, a multipart that was not split into parts (no boundary, or it does not occur in the body) and message/delivery-status are turned into text/plain (`_readable_parts`; a failure report is `name: value` lines). A part that ends without a closing line is closed by the next delimiter line of a multipart around it, as in the parser; an mbox is still split first and then read per mail (`_mail.mail_box`) | The standard-library parser checks every open boundary on every line: 900 levels + 200,000 lines (438 KB) took 18 s (even at the cap of 32 levels 5.8 s for 4 MB; 1.2 s at 1 level). The body of a multipart without a boundary and the recipient, status code and diagnostic of a delivery-failure report disappeared without a warning. Reading an mbox whole as one mail before splitting rejected a mailbox of 33 mails without closing boundaries | `test_core_malformed_mail_and_html.py::TestDeeplyNestedMultipart`, `TestMultipartWithoutUsableBoundary`, `test_core_mbox_markdown_and_api.py::TestMailboxOfMailsWithoutClosingBoundaries`, `test_audit_web_fixes.py::TestForwardScanOfHeaderLikeBodies`, `TestMultipartsInsideADeliveryReport` |
| Numeric attributes in mail and HTML (COUNT, INTERVAL, BYMONTHDAY of an event RRULE; colspan/rowspan; aria-colindex; the Google Docs list-level class) are read with `_package.decimal_int`. A null byte in a charset name makes it an unknown charset (`_encoding._declared_codec`, `_seven_bit_codec`) | For numbers over 4,300 digits `int()`, and for a charset with a null byte `codecs.lookup`, raise ValueError, so a single value rejected the whole mail or document as 'corrupted' | `test_core_malformed_mail_and_html.py::TestHugeNumbersInHtmlAndMail`, `TestCharsetWithANulByte` |
| In a `format=flowed` (RFC 3676) plain body, a line ending in a space (except the signature separator `-- `) is joined with the next line of the same quote depth (`_mail._unflowed`, `_mail_body` — common to the text and HTML extractors). With DelSp=yes that space is removed; the space stuffed at the start of a line is stripped and quoted lines take the `> ` form. Lines are not joined where the quote depth changes | It is the default of Thunderbird and Apple Mail, so continuous paragraphs were broken at every line | `test_core_word_lists_cell_blocks_and_mail_lines.py::TestFormatFlowedPlainMail` |
| In mails of a file that starts with an mbox separator line (mailbox, .eml saved by Thunderbird), one `>` is stripped from `>From ` at the start of body lines (mboxrd, `_mail._unescaped_from_lines`). It is stripped after the separator lines are found. Known accepted gap: in an old mboxo mailbox, a quoted line that was originally `>From` loses one `>` as well (the two rules cannot be told apart from the file alone). An .eml without a separator line is not changed | `>From here` stayed as is in the body read from a mailbox | `test_core_word_lists_cell_blocks_and_mail_lines.py::TestMailboxFromLineEscapes` |
| An RFC 2047 word that cannot be decoded stays as written and the mail is read | `HeaderParseError` is not a `ValueError`: `Subject: =?utf-8?b?A?=` rejected the whole mail | `test_audit_html_text.py::TestEncodedWordThatCannotBeDecoded` |
| An RFC 2231 boundary parameter (`boundary*=`, `boundary*0=`) is a boundary like any other in the nesting check: the value is the one the standard library resolves (`_mail._part_structure`), so its delimiter and closing lines close parts as an ordinary boundary's do. An empty boundary (`boundary=""`, delimiter line `--`) is a boundary too | The parser honours them, so 600 levels + 200,000 lines went around the 32-level cap (7–9 s). Counted as a level that only an enclosing ordinary boundary closed, the parts under such a boundary were never closed: 150 forwarded mails side by side were rejected as nested 100 levels deep. On an empty boundary the check failed with an error of its own and the mail was rejected as corrupted | `test_audit_html_text.py::TestMultipartNestingDeclaredWithExtendedParameters`, `test_audit_web_fixes.py::TestForwardLevelsFollowTheMultipartStructure`, `TestMultipartWithAnEmptyBoundary` |
| Names in the mail attachment warning are put on one line, control characters removed, and cut at 100 characters (`_mail._one_line`) | `filename*=utf-8''a%0Ab…` put line breaks and names of any length into the warning | `test_audit_html_text.py::TestAttachmentNameInTheWarning` |
| A forwarded mail whose own type is message/rfc822 (a forward of a forward with no multipart around it) has the mail inside read as a further forwarded mail (`_mail.mail_messages` looks at the mail itself too). Such a message has no body of its own (`_mail._is_forward`), so nothing is read twice. A mail whose top-level type is message/rfc822 is mail (`_mail._MAIL_CONTENT_TYPE`) | The innermost body vanished without a warning; a forwarded mail saved on its own was text, headers and all | `test_audit_web_fixes.py::TestForwardedMailThatIsItselfAForward`, `TestTopLevelForwardedMail` |
| Forwarded mails nested more than 100 levels deep are rejected as a corrupted document before parsing (`_mail._MAX_FORWARD_NESTING`, counted in the same pass as the multipart nesting). A level is a part the parser descends into as a mail: a message/* part other than a delivery report (message/rfc822, and any other message/ type — the parser treats them alike), or a part of a multipart/digest without a Content-Type, reached through the declared structure — the top-level header block, the header block after a delimiter line of an open multipart, or the header block of the mail inside such a part (its first line may be an mbox separator line, `From c@x Mon Sep  1 10:00:00 2025`). Only the first Content-Type header of a block counts. A delimiter or closing line of a multipart around it ends the level, so forwarded mails side by side do not add up. The same lines in a body, in a text attachment, or under a `--` line that is not a delimiter of an open multipart (a `-- ` signature line, `--- entry 3`, a quoted `--=_Part_7`) are text | The parser reads each level by recursion, and near a thousand levels the mail failed with a recursion error that depends on the stack in use. Counting every such line rejected a plain mail whose body quoted 120 of them; counting every header block under any `--` line rejected a plain mail, a text attachment or notes.txt quoting 150 MIME part headers, and looking for the end of each such block made a 1MB body of header-like lines take 12 s (0.1 s before) | `test_audit_web_fixes.py::TestDeeplyNestedForwardedMails`, `TestForwardLevelsFollowTheMultipartStructure`, `TestForwardScanOfHeaderLikeBodies` |
| In a mailbox read as text (a text extension), a mail whose body is HTML only gives its HTML body decoded, in source form (`text._mail_text(html_source=True)`, as for a forwarded mail), and the other mails are read as usual. A single such mail stays text in its original form, as before | One HTML-only mail left the whole archive as raw text: separator lines, MIME headers and the base64 bodies of the plain mails too | `test_audit_web_fixes.py::TestMailboxWithAnHtmlOnlyMailUnderATextName` |
| In a message read as MHTML that is a sent mail (`_mail.is_sent_mail`), the HTML read is the first body HTML part (`_html_mail._html_part` → `_mail.mail_html_body_parts`: attachments and forwarded mails excluded); only when there is none is the first text/html part read as before. Saved web pages keep the first text/html part | An attached `x.html` placed before the body was read instead of it, with a warning that it had not been read | `test_audit_web_fixes.py::TestHtmlAttachmentBeforeTheBodyOfAnMhtmlShapedMail` |
| A meeting invitation reads only the event's own properties: those of a component nested in the VEVENT (VALARM, with its own SUMMARY and ATTENDEE) are not read. A component that is opened and not closed before the event ends holds nothing — the lines after its BEGIN are the event's (`_mail_calendar._calendar_events`). Empty items of a recurrence rule (a trailing or doubled `;`) are skipped | An e-mail reminder written before the event's SUMMARY became the title and its recipient an attendee; `FREQ=WEEKLY;BYDAY=TU;` stayed raw. One stray `BEGIN:` line made the rest of the event (its place, its attendees) disappear without a warning | `test_audit_web_fixes.py::TestReminderInsideAnEvent`, `TestUnclosedComponentInsideAnEvent`, `TestRecurrenceRuleWithATrailingSemicolon` |
